# ภาคผนวก GDD: Game Balance & Anti-Griefing

> **สถานะ (docs/DECISIONS.md):** ⚠️ ใช้ invariants / safety floor / recovery path ใน MVP — ส่วนผู้เล่นหลายคนเป็นของระยะออนไลน์  
> ถ้าเนื้อหาในไฟล์นี้ขัดกับ [DECISIONS.md](../DECISIONS.md) ให้ยึด DECISIONS.md · ตัวเลขดู [BALANCE.md](../BALANCE.md)

ป้องกันการรบกวนโดยกลุ่มดาว โดยไม่ปิดกั้นเรื่องราวของโลก

**เกม:** พงศาวดารใต้ดวงดาว  
**รูปแบบ:** โลกออนไลน์ร่วมกัน ผู้เล่นรับบทเป็นกลุ่มดาวและมีอิทธิพลต่อ NPC/ชุมชน  
**เวอร์ชัน:** 0.1 — ข้อเสนอสำหรับต้นแบบ  
**เป้าหมาย:** ป้องกันผู้เล่นคนเดียวหรือกลุ่มย่อยทำลายอารยธรรม NPC อย่างถาวร ขณะยังเปิดพื้นที่ให้เกิดความล้มเหลว ความขัดแย้ง และผลลัพธ์ที่ไม่สมบูรณ์แบบ

**หลักสมดุล:** ผู้เล่นมีอำนาจสร้างแรงกดดันและเปลี่ยนทิศทางของเหตุการณ์ได้ แต่ไม่ควรมีอำนาจลบความสามารถของ NPC/ชุมชนในการตัดสินใจ ฟื้นตัว และสร้างเรื่องราวต่อ

## 1. คำจำกัดความและเส้นแบ่งของการเล่น

### 1.1 การเล่นเชิงวุ่นวายที่ยอมรับได้

กลุ่มดาวอาจสนับสนุนแนวทางที่เสี่ยง เห็นต่างกับผู้เล่นอื่น หรือทำให้เกิดผลเสียบางอย่าง หากการกระทำนั้น:

- อยู่ในกฎที่เปิดเผยและระบบอนุญาต

- มีต้นทุน/ความเสี่ยงชัดเจนก่อน commit

- ไม่มุ่งทำลายบัญชีหรือประสบการณ์ของผู้เล่นรายอื่น

- NPC ยังมีสิทธิ์ปฏิเสธหรือเลือกทางอื่น

- ผลเสียมีขอบเขตและโลกมีทางฟื้นตัว

ตัวอย่าง: สนับสนุนให้กิลด์เสี่ยงสำรวจเหมืองแทนการใช้เงินซ่อมสะพาน ซึ่งอาจทำให้การค้าชะลอ แต่ยังมีทางเลือกและผลลัพธ์ตรวจสอบได้

### 1.2 การก่อกวน (Griefing)

พฤติกรรมที่ใช้ระบบเพื่อรบกวน/ทำลายประสบการณ์โดยไม่ใช่การตัดสินใจในเกมอย่างสุจริต เช่น:

- สแปมการแทรกแซงเพื่อให้ notification รบกวนผู้เล่นอื่น

- ใช้บัญชีเสริมหรือกลุ่มประสานกันเพื่อทะลุเพดานระบบ

- พยายามทำให้ชุมชนขาดทรัพยากรพื้นฐานหรือบริการถาวร

- ใช้ข้อความ/การตั้งชื่อเพื่อคุกคามผู้เล่นอื่น

- ใช้บั๊กหรือคำขอซ้ำเพื่อสร้างเงิน/ทรัพยากรหรือก่อความเสียหาย

- จงใจล็อกผู้อื่นออกจาก Raid, NPC หรือกิจกรรมร่วม

### 1.3 ความล้มเหลวในเกมไม่เท่ากับ griefing

การเลือกผิด การเสี่ยง หรือสนับสนุนทางเลือกที่ไม่สำเร็จไม่ควรถูกลงโทษเป็น griefing โดยอัตโนมัติ ระบบแยก **ผลการเล่นที่ไม่ดี** ออกจาก **รูปแบบการใช้งานที่มุ่งรบกวน/หลบเลี่ยงกฎ** โดยดูบริบทและหลักฐาน

## 2. หลักประกันขั้นต่ำของอารยธรรม

โลกต้องมีขอบเขตความเสียหายที่ไม่มีผู้เล่นคนเดียวหรือกลุ่มเล็กทะลุได้

### 2.1 Invariants ที่ห้ามถูกทำลายโดยการแทรกแซงผู้เล่นโดยตรง

1.  **ไม่มีการลบชุมชนหลักถาวร:** หมู่บ้าน/เมืองแกนหลักไม่ถูกลบออกจากโลกด้วยพลังกลุ่มดาวเพียงอย่างเดียว

2.  **ไม่มีการทำให้บริการจำเป็นหายถาวร:** อาหารพื้นฐาน การรักษาขั้นต้น และการเดินทางขั้นต่ำต้องมีทางกลับมา

3.  **ไม่มีการฆ่าหรือบังคับออกจากโลกของ NPC เป้าหมายด้วยพลังผู้เล่นโดยตรง**

4.  **ไม่มีการสร้างเงิน/อาหาร/อาวุธจากศูนย์อย่างไม่จำกัด**

5.  **ไม่มีการล็อกผู้เล่นอื่นออกจาก NPC/ภารกิจ/พงศาวดาร**

6.  **ไม่มีการใช้พลังกลุ่มดาวเปลี่ยนการตัดสินใจที่เป็นไปไม่ได้ให้เกิดขึ้นได้**

7.  **ทุกวิกฤตมีเส้นทางการฟื้นฟูอย่างน้อยหนึ่งทางที่ NPC ทำได้เอง**

### 2.2 อารยธรรมเปลี่ยนแปลงได้ แต่ไม่ถูกลบ

อารยธรรมอาจถดถอย เสียเมือง ถูกย้ายศูนย์กลาง เปลี่ยนผู้นำ หรือกลายเป็นซากประวัติศาสตร์ได้ในเหตุการณ์ใหญ่ที่มาจากระบบโลกและมีสาเหตุสะสมชัดเจน แต่:

- ต้องมีสัญญาณเตือนและการตอบสนองหลายช่วง

- ไม่เกิดจากคำสั่งของกลุ่มดาวคนเดียว

- ต้องมีโหมด/บทต่อเนื่องหลังความเปลี่ยนแปลง

- เก็บประวัติและทางเลือกฟื้นฟูไว้

- ไม่ยึดทรัพยากร/ความก้าวหน้าส่วนตัวของผู้เล่น

### 2.3 กำแพงความเสียหายแบบหลายชั้น

ใช้หลายกลไกร่วมกัน ไม่พึ่งแค่การคืนสถานะอัตโนมัติ:

- **เพดานอิทธิพล:** จำกัดผลสูงสุดของกลุ่มดาวต่อเหตุการณ์

- **NPC agency:** NPC ปฏิเสธการชี้นำที่ขัดกับเป้าหมาย/ความเป็นไปได้

- **resilience ของชุมชน:** safety stock ผู้สืบทอด และบริการสำรอง

- **recovery path:** ภารกิจ/การค้า/การย้ายถิ่น/การเปลี่ยนสถาบันเพื่อฟื้น

- **event director:** ป้องกันวิกฤตซ้อนเกินกำลัง

- **server validation:** ไม่มี client ใดแก้ผลหรือบัญชีทรัพยากรโดยตรง

## 3. ชั้นอำนาจของกลุ่มดาว

จัดการกระทำตามผลกระทบ ไม่ใช่ตามชื่อพลัง

| ชั้น                               | ตัวอย่าง                              | ความเสี่ยง | กติกา                                                          |
|----------------------------------|-------------------------------------|----------|---------------------------------------------------------------|
| **0 — สังเกต/ข้อมูล**               | จับตามอง อ่านพงศาวดาร พยากรณ์          | ต่ำ       | ต้นทุนต่ำ/ฟรีได้ แต่ไม่เปลี่ยนสถานะโลกโดยตรง                           |
| **1 — สนับสนุนเล็กน้อย**             | ส่งลาง พรด้านกำลังใจ                   | ต่ำ–กลาง  | จำกัดตาม cooldown และ target lock                              |
| **2 — เปลี่ยนผลเฉพาะเหตุการณ์**      | พิทักษ์ ของขวัญพื้นฐาน อวตาร Raid         | กลาง     | มีต้นทุน มี cap ต่อผู้เล่นและต่อ event                                 |
| **3 — ผลต่อชุมชน/สถาบัน**           | ชี้นำโครงการสาธารณะ เปลี่ยนลำดับความสำคัญ | สูง       | ผ่านการตัดสินใจ NPC/องค์กร ต้องมีต้นทุนและผลแลกเปลี่ยน                  |
| **4 — เปลี่ยนยุค/โครงสร้างอารยธรรม** | ยุบรัฐ ย้ายเมือง ทำลายสถาบัน             | วิกฤต     | ไม่มีเป็นพลังผู้เล่นโดยตรงใน MVP; ทำได้เฉพาะ Event Director/ผลสะสมโลก |

หลักการสำคัญ

กลุ่มดาวไม่มีปุ่ม “ทำลายเมือง/สั่งประหาร/ล้มอาณาจักร” ในโลกหลัก ผู้เล่นสามารถสนับสนุนทางเลือกทางการเมืองหรือการรับมือภัยได้ แต่ผลเกิดผ่านการตัดสินใจและข้อจำกัดของ NPC/สถาบัน

## 4. เพดานผลของการแทรกแซง

### 4.1 เพดานรายบุคคล

อ้างอิงระบบอิทธิพลที่ออกแบบไว้:

- อิทธิพลสูงสุด 100; ฟื้นตามเวลาจริง

- ผู้เล่นหนึ่งคนสนับสนุน event เดียวได้ไม่เกิน 30 อิทธิพล

- พลังระดับสูงจำกัดหนึ่งครั้งต่อผู้เล่นต่อ event

- มีคูลดาวน์รายพลังและคูลดาวน์พลังแรง

- ไม่มีการซื้ออิทธิพลหรือซื้อการลด cooldown ด้วยเงินจริง

### 4.2 เพดานรวมต่อเป้าหมาย/เหตุการณ์

- ผลเปลี่ยนโอกาสสำเร็จจากกลุ่มดาวรวมไม่เกินค่าที่กำหนด เช่น +15 จุดเปอร์เซ็นต์

- ผลลดความเสียหายรวมไม่เกิน 20% ต่อ hazard

- ผลผลิตที่เกิดจากการสนับสนุนไม่เกิน 10% ต่อกิจการต่อวันเกม

- ผลหมวดเดียวกันไม่ stack เต็ม; ใช้ diminishing returns

- สินค้าจากกลุ่มดาวมีเพดานต่อผู้รับและต่อช่วงเวลา และไม่สร้างเงินสด

ค่าจริงต้องแสดงใน UI ก่อนยืนยัน ไม่ซ่อนไว้ในกฎเซิร์ฟเวอร์

### 4.3 เพดานความเสียหายต่อชุมชน

กำหนด <u>civilization_integrity</u> เป็นชุดมาตรวัดแยกตามชุมชน ไม่ใช่ HP รวมที่ผู้เล่นกดลดได้:

- อาหาร/น้ำ/ยา

- ที่อยู่อาศัยและโครงสร้างพื้นฐาน

- ประชากรและแรงงาน

- ความปลอดภัย

- ความชอบธรรม/ความร่วมมือ

- ความสามารถบริหาร/สืบทอด

การกระทำกลุ่มดาวหนึ่งครั้งเปลี่ยนได้เฉพาะ track ที่เกี่ยวข้อง และมีขอบเขตต่อ event หนึ่ง หากค่าชุมชนลงต่ำกว่า threshold ระบบเปิด recovery action/สำรองที่มีต้นทุนจริงและแจ้งที่มา ไม่คืนค่าขึ้นเงียบ ๆ

## 5. นโยบายต่อพลังเชิงลบและการเล่นสายวุ่นวาย

### 5.1 MVP: ไม่มีการทำลายโดยตรง

ใน MVP ไม่ให้กลุ่มดาว:

- ทำลายทรัพย์สิน/สินค้า NPC โดยตรง

- ทำให้ NPC บาดเจ็บ เสียชีวิต หรือถูกขับออกจากชุมชนโดยคำสั่ง

- สร้างโรค ภัยแล้ง หรือมอนสเตอร์บุกด้วยตนเอง

- สาป/ลบพลังของกลุ่มดาวอื่น

- สร้างความอดอยากหรือปิดบริการจำเป็นโดยตรง

ผู้เล่นยังสามารถสนับสนุนทางเลือกที่เสี่ยงหรือผลเสียทางอ้อมได้ หากเป็นตัวเลือกที่มีเหตุผลในเหตุการณ์และ NPC/ชุมชนรับรู้ผลแลกเปลี่ยน

### 5.2 หากเพิ่ม “แนวทางโกลาหล” ในอนาคต

ทำให้เป็น **event modifier แบบจำกัดและเปิดเผย** ไม่ใช่พลังทำลายเป้าหมาย:

- ใช้ได้ในพื้นที่/บทที่ระบุว่าอนุญาตให้เกิดผลเสี่ยงสูง

- ไม่ทำให้ความเสียหายถาวรเกิน safety floor

- ใช้ทรัพยากร/โอกาสของโลกตามบัญชีที่ระบุ

- มี telegraph และ counterplay จาก NPC/ชุมชน

- ต้องผ่านข้อกำหนดจำนวนเงื่อนไขโลก ไม่ใช่คะแนนผู้เล่นอย่างเดียว

- ผลที่รุนแรงที่สุดต้องเกิดจากความล้มเหลวสะสมหลายระยะ ไม่ใช่ action ครั้งเดียว

### 5.3 เล่นในพื้นที่ทดลอง

หากต้องการให้ผู้เล่นลองผลกระทบสุดโต่ง ให้ทำใน:

- โลกจำลอง/พื้นที่ sandbox ที่แยกจากโลกหลัก

- บท/ฤดูกาลที่ผู้เล่นเลือกเข้าร่วมและเห็นกติกาก่อนเริ่ม

- การจำลองย้อนหลังที่ไม่มีผลต่อเศรษฐกิจหรือ NPC ถาวร

ไม่ควรใช้โลกหลักเป็นสนามทดลองโดยไม่มี opt-in

## 6. ระบบ Resilience และ Recovery ของชุมชน

### 6.1 Safety floors

ตั้งระดับขั้นต่ำสำหรับบริการหลัก แต่ไม่ให้เป็น immortality:

- **อาหาร:** มีช่องทางอย่างน้อยหนึ่งช่อง เช่น safety stock, นำเข้า, สินค้าทดแทน หรือย้ายถิ่น

- **การรักษา:** มีผู้รักษา/ความรู้พื้นฐาน/การส่งตัวไปชุมชนอื่น

- **ความปลอดภัย:** มีทางหนี/จุดปลอดภัย แม้ยามหรือกิลด์อ่อนกำลัง

- **การบริหาร:** มีผู้รักษาการ/สภาชั่วคราวหากผู้นำไม่อยู่

- **ความรู้:** สูตรหรือบริการจำเป็นมีสำเนาในสถาบัน/ผู้ฝึกอย่างน้อยหนึ่งแห่งเมื่อผ่านการพัฒนาแล้ว

Safety floor ไม่ทำให้ทุกอย่างกลับสภาพเดิมทันที แต่ป้องกันการลบช่องทางฟื้นทั้งหมด

### 6.2 Recovery budget

คลัง/ชุมชนมีงบฉุกเฉินจำกัด ใช้เมื่อระบบเข้าสู่ภาวะวิกฤต:

- เปิดคลังสำรอง

- จัดงานชั่วคราว

- ย้ายครัวเรือนไปพื้นที่ปลอดภัย

- ขอความช่วยเหลือจากเมือง/กิลด์อื่น

ทุกครั้งบันทึกต้นทุน เช่น หนี้ชุมชน งบซ่อมที่เลื่อน หรือสินค้าในคลังลดลง

### 6.3 Recovery quests

หลังผลลัพธ์เสียหาย ระบบสร้างภารกิจฟื้นฟู เช่น:

- ซ่อมสะพาน/คลัง/ระบบน้ำ

- นำเข้าอาหาร/ยา

- ฝึกผู้รักษาหรือผู้สืบทอดกิจการ

- ไกล่เกลี่ยความขัดแย้ง

- สำรวจสาเหตุและป้องกันภัยครั้งถัดไป

ผู้เล่นกลุ่มดาวช่วยสนับสนุนได้ แต่ไม่จำเป็นต้องเป็นผู้แก้ทุกอย่าง และภารกิจไม่ให้ของรางวัลซ้ำแบบฟาร์มได้

## 7. ป้องกันการใช้บัญชีเสริม/การประสานกันเพื่อทะลุเพดาน

### 7.1 อย่าพึ่งเพดานต่อบัญชีอย่างเดียว

หากมีเพียงเพดานต่อผู้เล่น ผู้ใช้บัญชีเสริมอาจข้ามข้อจำกัดได้ จึงต้องมี **เพดานผลรวมต่อ event/เป้าหมาย** ที่ไม่ขึ้นกับจำนวนบัญชี เพดานนี้เป็นแนวป้องกันหลัก

### 7.2 รางวัลไม่ผูกกับจำนวนบัญชีหรือแต้มที่ใช้

- event เดียวให้รางวัลความก้าวหน้าหลักหนึ่งครั้งต่อบัญชี และเน้น cosmetic/Chronicle

- ไม่แจกเงินหรืออิทธิพลตามการเข้าร่วมซ้ำ

- ไม่ให้วงดาวสร้างคะแนนเชิงพลังจากบัญชีสมาชิกใหม่

- การมีส่วนร่วมแสดงเป็นหมวด/สรุป ไม่จัดอันดับจากการใช้แต้ม

### 7.3 การตรวจพฤติกรรมผิดปกติ

สัญญาณให้ตรวจสอบ (ไม่ใช้ตัวใดตัวหนึ่งลงโทษอัตโนมัติ):

- คำสั่งซ้ำเร็วผิดปกติหรือ idempotency mismatch

- กลุ่มบัญชีใช้รูปแบบ action เดียวกันเพื่อทะลุเพดานที่ควรจำกัด

- การเข้าออก Raid เพื่อจอง/บล็อก slot ซ้ำ

- รูปแบบสร้างเหตุการณ์/ภารกิจซ้ำเพื่อรับ reward

- ความพยายามแก้ค่าจาก client หรือส่งข้อมูลที่ไม่อยู่ใน schema

มาตรการเริ่มต้นคือ rate limit, ปฏิเสธธุรกรรมซ้ำ, จำกัดเฉพาะ action เสี่ยง และให้ทีมตรวจ log ก่อนระงับบัญชีถาวร

### 7.4 ปกป้องความเป็นส่วนตัว

- ไม่ใช้ IP address เป็นหลักฐานเดียว เพราะครัวเรือน/เครือข่ายเดียวกันอาจมีหลายคน

- ไม่เปิดเผยบัญชีที่ระบบสงสัยต่อสาธารณะ

- เก็บข้อมูลการตรวจสอบเท่าที่จำเป็นและกำหนดระยะเวลาเก็บ

- มีช่องทางอุทธรณ์หากการจำกัด action กระทบผู้เล่นปกติ

## 8. ป้องกันการยึดครองและการล็อกเป้าหมาย

- ไม่มีสิทธิ์ผูกขาด NPC จากการเป็นผู้ติดตามก่อน

- cooldown/target lock ใช้กับผลกระทบ ไม่ใช่แค่ชื่อพลัง เพื่อป้องกันสลับพลังหลบกฎ

- NPC ที่รับการสนับสนุนหมวดหนึ่งเต็มแล้ว ยังมีทางช่วยชุมชน/ภารกิจอื่น

- ถ้า Raid มีจำนวนอวตารจำกัด ผู้เล่นที่เข้าทีหลังมี remote support หรือคิวสำรอง ไม่ถูกตัดจากโลกทั้งหมด

- ผู้เล่นไม่สามารถใช้พลังทำให้ NPC ยกเลิกความสัมพันธ์หรือกิลด์ของผู้เล่นอื่นโดยตรง

- ไม่มีการ “จอง” NPC ด้วยการส่งแต้มที่หมดอายุหรือสถานะส่วนตัว

## 9. การตรวจจับและการตอบสนองต่อ griefing

### 9.1 ระดับการตอบสนอง

| ระดับ               | ตัวอย่าง                                   | มาตรการ                                     |
|--------------------|------------------------------------------|---------------------------------------------|
| 0 — ปกติ            | เลือกแผนเสี่ยงที่ระบบอนุญาต                    | ไม่มีการลงโทษ; แสดงผลตามจริง                   |
| 1 — รูปแบบถี่/ผิดพลาด  | ส่งคำขอซ้ำ, กด action ที่ใช้ไม่ได้จำนวนมาก      | แจ้งเตือน, rate limit ชั่วคราว                  |
| 2 — หลบกฎ/รบกวนซ้ำ  | พยายามใช้ exploit หรือบล็อกกิจกรรมต่อเนื่อง     | จำกัด action เฉพาะ, ตรวจ log, แจ้งผู้เล่น        |
| 3 — คุกคาม/โจมตีระบบ | ใช้ข้อความคุกคาม, exploit ทำลายข้อมูล/เศรษฐกิจ | moderation ตามกฎแพลตฟอร์ม, ระงับบัญชีเมื่อมีหลักฐาน |

การตัดสินใจลงโทษต้องใช้หลักฐานจาก server log และแยกความผิดพลาด/ผลเกมปกติออกจากการจงใจหลบกฎ

### 9.2 เครื่องมือผู้เล่น

- mute/block ผู้เล่นในช่องสื่อสาร

- ซ่อนชื่อกลุ่มดาวอื่นใน UI

- ปิดการแจ้งเตือนการสนับสนุนที่ไม่เกี่ยวกับ watchlist

- report ข้อความ/การรบกวนพร้อม event ID

- เลือกไม่เข้าร่วมพื้นที่หรือโหมดทดลองที่มีความเสี่ยงสูง

การ block ควบคุมการสื่อสารและการมองเห็น ไม่ควรลบผลลัพธ์โลกที่เกิดขึ้นจริงตามกติกา

## 10. สมดุลระหว่างอิสระกับความปลอดภัย

### 10.1 ใช้ friction ตามระดับผลกระทบ

- ข้อมูล/การสังเกต: friction ต่ำ

- พลังช่วยเฉพาะเหตุการณ์: confirmation และ cooldown ปกติ

- ผลต่อชุมชน/สถาบัน: ต้องแสดงต้นทุน/ผลข้างเคียง และผ่านการตัดสินใจ NPC

- ผลต่ออารยธรรม/ยุค: ไม่เปิดเป็น action โดยตรง; ต้องเกิดจากสาเหตุสะสม/Global Event ที่มีหลายขั้น

### 10.2 ไม่ใช้การยับยั้งเงียบ

ถ้าระบบปฏิเสธ/ลดผล ให้บอกเหตุผล เช่น:

- “ผลป้องกันหมวดนี้เต็มเพดานแล้ว”

- “NPC ไม่มีข้อมูลพอจะเชื่อคำเตือนนี้”

- “คลังชุมชนไม่มีสินค้าให้มอบ”

- “การตัดสินใจนี้ทำไม่ได้เพราะไม่มีแรงงาน/งบรองรับ”

### 10.3 ไม่ทำให้โลกไร้ความเสี่ยง

Anti-griefing ไม่ได้แปลว่าปกป้อง NPC จากความล้มเหลวทุกชนิด NPC ยังบาดเจ็บ กิจการปิด กิลด์แตก หรือรัฐเปลี่ยนแปลงได้ หากเกิดจากการจำลองที่มีเหตุผลหลายขั้นและมีโอกาสรับมือ

## 11. ตาราง Threat Model

| ภัย/การใช้งานผิด         | ผลเสียที่อาจเกิด           | มาตรการหลัก                                                       |
|-----------------------|------------------------|------------------------------------------------------------------|
| กลุ่มดาวคนเดียวสแปมพร    | NPC แข็งแกร่ง/ไม่เสี่ยง     | cooldown, cap ต่อคน, cap รวม, diminishing returns                 |
| หลายบัญชีรุม NPC         | ทะลุผลรวมรายบัญชี         | global target/event cap, ไม่มีรางวัลตามจำนวนบัญชี                     |
| จงใจทำให้ราคาพุ่ง        | เศรษฐกิจเสีย             | ผู้เล่นไม่ซื้อขายตรงใน MVP, ราคา server-derived, ขอบเขต ±10%/วัน        |
| พยายามทำลายคลังชุมชน    | ขาดบริการจำเป็น          | ไม่มีพลังทำลายโดยตรง, ledger, safety floor, recovery stock          |
| บล็อก Raid slot        | คนอื่นเข้าไม่ได้            | จำกัด avatar slots พร้อม remote support/คิวสำรอง, ตรวจการจอง        |
| สร้าง event ซ้ำเพื่อฟาร์ม  | เงิน/ของเฟ้อ             | event_id, unique reward, ไม่มีรางวัลหลักซ้ำ                           |
| สร้างข้อความคุกคาม       | ทำร้ายประสบการณ์ผู้เล่น     | preset messages ใน MVP, mute/block/report หากเพิ่ม chat            |
| ใช้บั๊ก/คำขอซ้ำ           | สร้างผลซ้ำ/เงินติดลบ       | server authority, atomic transaction, idempotency                |
| ผลลัพธ์ล้มเหลวจาก NPC AI | ผู้เล่นเข้าใจผิดว่าโดน grief | Decision trace, Chronicle reason, support ticket/event reference |

## 12. ตัวชี้วัดสมดุลและ Anti-Griefing

ติดตามระดับโลกและ event โดยไม่ใช้ตัวเลขเหล่านี้ลงโทษผู้เล่นอัตโนมัติ:

- เปอร์เซ็นต์ของผลลัพธ์ที่ถูกเปลี่ยนโดยพลังกลุ่มดาว

- จำนวน event ที่ผลรวมถึง cap

- ความถี่การใช้พลังซ้ำกับ NPC/พื้นที่เดิม

- จำนวนการปฏิเสธ action ด้วยเหตุผลแต่ละประเภท

- อัตราอาหาร/ยา/บริการพื้นฐานต่ำกว่า safety floor

- เวลาฟื้นตัวเฉลี่ยหลัง Global Event

- จำนวนคำขอผิดรูปแบบ/ซ้ำ/ถูก rate limit

- จำนวนกรณีที่ผู้เล่นรายงานและผลการตรวจสอบ

- ความต่างของผลลัพธ์ระหว่างผู้เล่นเดี่ยวกับวงดาวใหญ่

- สัดส่วนผู้เล่นที่รู้สึกว่าอิทธิพลของตนมีความหมายแต่ไม่ครอบงำโลก

หากพบว่าเหตุการณ์ส่วนใหญ่ถูกกลุ่มดาวแก้ได้หมด ให้ลดผลรวมของพลังหรือเพิ่มบทบาทการเตรียมตัว NPC ก่อนเพิ่มความยาก หากพบว่ากลุ่มดาวไม่มีผลเลย ให้ทำผลระยะสั้นอ่านง่ายขึ้นแทนการยกเลิกเพดานทั้งหมด

## 13. ขอบเขต MVP ที่แนะนำ

ต้องมี

- allowlist ของพลังและ tier ผลกระทบ

- cap ต่อผู้เล่น/ต่อ event/ต่อเป้าหมาย

- diminishing returns และ cooldown รวมสำหรับพลังแรง

- NPC agency พร้อมเหตุผลที่อ่านได้

- safety floors และ recovery paths สำหรับอาหาร การรักษา ความปลอดภัย และการบริหาร

- server authority, transaction log, idempotency และ rate limit

- event director จำกัดวิกฤตซ้อน

- mute/block/report สำหรับช่องทางสื่อสาร

- dashboard ภายในสำหรับตรวจเศรษฐกิจและความเสียหาย

ยังไม่ทำ

- พลังที่ผู้เล่นสร้างภัยพิบัติหรือทำลายเมืองโดยตรง

- ระบบลงโทษจากคะแนนอัตโนมัติที่ไม่อธิบายเหตุผล

- player-vs-player sabotage

- การขายพลัง/การลด cooldown ด้วยเงินจริง

- การรีเซ็ตโลกทันทีเมื่อมีผู้เล่นก่อกวน

## 14. เกณฑ์ทดสอบก่อนเปิดทดสอบสาธารณะ

1.  จำลองผู้เล่นหนึ่งคนใช้พลังทุกครั้งที่ cooldown หมด: ไม่สามารถทำให้บริการพื้นฐานหายถาวร

2.  จำลองหลายบัญชีสนับสนุนเป้าหมายเดียว: ผลรวมยังติด global cap

3. จำลองผู้เล่นกลุ่มดาวหลายฝ่ายสนับสนุนทางเลือกตรงข้าม: NPC เลือกโดยใช้เป้าหมาย/ทรัพยากรและมีเหตุผล

4. ปิดการเข้าร่วมของผู้เล่นทั้งหมด: NPC ยังมีทางรับมือและโลกยังดำเนินต่อ

5. จำลองเศรษฐกิจหลังภัย: ไม่มีเงิน/สินค้าสร้างซ้ำจาก reward หรือ recovery loop

6. ทดสอบผู้เล่นออนไลน์ถี่เทียบผู้เล่นที่กลับมาหลังหลายวัน: ไม่มีความได้เปรียบถาวรจากการเฝ้าจอ

7. ทดสอบคำขอซ้ำ/ตัดการเชื่อมต่อ/กดยืนยันสองครั้ง: ไม่หักอิทธิพลซ้ำ

8. ทดสอบกรณีผลลัพธ์เสียหาย: มี ledger, event log และ recovery path

9. ทดสอบข้อความ/การรายงาน: ผู้เล่นบล็อกการรบกวนได้โดยไม่ทำให้ระบบโลกเสีย

10. ให้ผู้ทดสอบอธิบายได้ว่ากลไกใดป้องกันการทำลายและกลไกใดเปิดให้ผลลัพธ์เสี่ยงเกิดขึ้น

## 15. ข้อสรุปเชิงออกแบบ

การป้องกัน griefing ที่ดีไม่ควรทำให้กลุ่มดาวทุกดวงมีพลังเหมือนกันหรือไม่มีผล แต่ควรทำให้ **พลังเชิงลบมีขอบเขต พลังรวมมีเพดาน และชุมชนมีความสามารถฟื้นตัว**

ข้อเสนอสำหรับ MVP คือ:

- ไม่มีการทำลายโดยตรงจากผู้เล่น

- ให้กลุ่มดาวสนับสนุนทางเลือกในเหตุการณ์ที่มีเหตุผล

- ใช้เพดานผลรวม ไม่พึ่ง cap ต่อบัญชีอย่างเดียว

- สร้าง safety floor/recovery โดยมีต้นทุนที่บันทึกได้

- ให้ NPC และสถาบันรับมือเองได้ แม้ไม่มีผู้เล่น

- แยกพฤติกรรมวุ่นวายที่เป็นส่วนหนึ่งของเกมออกจากการหลบกฎ/คุกคาม

**หลักตรวจสอบสุดท้าย:** ผู้เล่นคนเดียวอาจทำให้เรื่องราวยุ่งยากขึ้นได้ แต่ไม่ควรมีอำนาจทำให้ผู้เล่นทั้งโลกไม่มีอะไรเหลือให้เล่นต่อ
