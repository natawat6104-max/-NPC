Global Events — ภัย วิกฤต และการรับมือร่วมกันของกลุ่มดาว

**เกม:** พงศาวดารใต้ดวงดาว  
**รูปแบบ:** โลกออนไลน์ร่วมกัน; NPC ขับเคลื่อนชีวิต เศรษฐกิจ และสังคม ส่วนกลุ่มดาวสนับสนุนได้โดยไม่สั่งการโดยตรง  
**เวอร์ชัน:** 0.1 — ข้อเสนอสำหรับต้นแบบ  
**เป้าหมาย:** ใช้เหตุการณ์ใหญ่เป็น “stress test” ของเศรษฐกิจ สายส่งสินค้า ความสัมพันธ์ กิลด์/Factions การปกครอง และระบบความร่วมมือระหว่างกลุ่มดาว

**หลักคิด:** Global Event ไม่ใช่แถบพลังชีวิตของบอสที่รอให้ผู้เล่นคลิก แต่เป็นวิกฤตที่มีสาเหตุ สัญญาณเตือน ผลกระทบหลายระบบ ทางรับมือหลายแบบ และผลลัพธ์ที่เกิดได้แม้ผู้เล่นไม่ออนไลน์

## 1. เป้าหมายการออกแบบ

ระบบ Global Events ต้อง:

1.  สร้างสถานการณ์ที่ **ทดสอบระบบจำลองจริง** เช่น ผลผลิต การขนส่ง งบชุมชน ความไว้ใจ และการสืบทอดบทบาท

2.  มีสัญญาณเตือนและข้อมูลที่เพียงพอให้ NPC/ผู้เล่นตัดสินใจ ไม่ใช่ลงโทษแบบไม่มีที่มา

3.  รองรับหลายวิธีรับมือ ไม่บังคับให้ทุกคนต่อสู้หรือใช้พลังกลุ่มดาว

4.  ให้ NPC และสถาบันเริ่มตอบสนองเอง แม้ผู้เล่นไม่เข้าร่วม

5.  สร้างผลระยะสั้นและระยะยาวที่ติดตามได้ในพงศาวดาร

6.  จำกัดจำนวนเหตุการณ์ให้เซิร์ฟเวอร์และผู้เล่นรับมือได้

7.  ทำให้ความร่วมมือมีคุณค่า แต่ไม่ให้จำนวนผู้เล่น/แต้มอิทธิพลเป็นตัวกำหนดชัยชนะโดยตรง

เงื่อนไขออกแบบที่ต้องรักษา

- เหตุการณ์สุ่มต้อง **มีเงื่อนไขโลกเป็นตัวกำหนดน้ำหนัก** ไม่สุ่มภัยร้ายแรงจากศูนย์

- ไม่มี event เดียวที่ทำให้สูญเสียอาหาร ยา ที่อยู่อาศัย หรือ NPC สำคัญจำนวนมากโดยไม่มีช่วงเตือน/ทางรับมือ

- หากไม่มีผู้เล่นตอบสนอง โลกยังมีเส้นทางแก้ไขผ่าน NPC และองค์กร แต่อาจเกิดผลเสียมากกว่า

- หากผู้เล่นสนับสนุนเต็มที่ ก็ไม่ควรลบผลกระทบทั้งหมดหรือทำให้ภัยไม่มีความหมาย

- ความยากไม่สเกลขึ้นเพียงเพราะมีผู้เล่นจำนวนมากออนไลน์

## 2. นิยาม Global Event

Global Event คือเหตุการณ์ระดับภูมิภาคหรือหลายชุมชนที่:

- มี trigger/สาเหตุเชิงโลกที่ระบุได้

- กระทบอย่างน้อย 2 ระบบ เช่น เศรษฐกิจและความปลอดภัย หรือประชากรและความชอบธรรม

- มีระยะเวลาและสถานะชัดเจน

- เปิดให้ NPC องค์กร ชุมชน และกลุ่มดาวตอบสนอง

- มีผลลัพธ์หลายระดับและพงศาวดารบันทึกสาเหตุ–ผล

คำว่า “Global” หมายถึงผู้เล่นทุกคนในโลกเดียวกันรับรู้เหตุการณ์เดียวกัน ไม่จำเป็นต้องหมายถึงภัยกระทบทุกโหนดพร้อมกัน

## 3. ตัวจัดการเหตุการณ์ระดับโลก (World Event Director)

### 3.1 หน้าที่

Event Director ตรวจสถานะโลกและเลือกว่าจะ:

- เปิดสัญญาณเตือนใหม่

- ยกระดับ event ที่กำลังดำเนิน

- ปล่อยให้ event คลี่คลาย/เข้าสู่ช่วงฟื้นฟู

- งดเหตุการณ์ใหม่เมื่อโลกกำลังรับภาระสูง

ไม่ควรสุ่มเหตุการณ์ทุกวันด้วยโอกาสคงที่ เพราะจะเกิดภัยซ้อนโดยไม่สัมพันธ์กับการเล่น

### 3.2 ระบบคะแนนความเสี่ยง

แต่ละ archetype มีตัวแปรที่เพิ่ม/ลดความเสี่ยง เช่น:

> risk_score(event_type, region) = base_risk
>
> \+ world_condition_modifiers
>
> \+ unresolved_pressure
>
> \- recent_resolution_relief
>
> \- event_cooldown_relief

ตัวอย่าง:

- ภัยแล้ง: ฝนต่ำต่อเนื่อง + คลังอาหารลด + พื้นที่เกษตรพึ่งแหล่งน้ำเดียว

- โรคพืช: ความหลากหลายพืชต่ำ + ฤดูเหมาะกับศัตรูพืช + เมล็ดสำรองน้อย

- ฝูงมอนสเตอร์อพยพ: แหล่งที่อยู่อาศัยถูกทำลาย + ภัยในป่าเพิ่ม + เส้นทางเดินสัตว์ถูกปิด

- วิกฤตการค้า: เส้นทางอันตราย + พ่อค้าหยุดเดินทาง + สินค้าจำเป็นลด

### 3.3 การเลือกเหตุการณ์

1.  ตรวจว่ามี event ที่ยัง active และถึงเพดานโลกหรือไม่

2.  ตรวจ cooldown ของชนิด event และภูมิภาค

3. คำนวณ risk score เฉพาะ event ที่มีเงื่อนไขรองรับ

4. เลือกตาม weight โดยใช้ world seed

5. ตรวจซ้ำว่ามีเวลา/ทางเลือกตอบสนองและไม่ซ้อนกับภัยหนักเกินไป

6. สร้าง telegraph phase ก่อนเข้าสู่ผลกระทบเต็ม

### 3.4 เพดานจำนวนเหตุการณ์

ค่าตั้งต้นสำหรับต้นแบบ:

- เหตุการณ์วิกฤตระดับสูง active ได้ครั้งละ **1 เหตุการณ์ต่อภูมิภาค**

- โลกหนึ่งมีวิกฤตระดับสูง active พร้อมกันได้ไม่เกิน **2 เหตุการณ์** ในช่วง MVP

- มีเหตุการณ์รองได้ แต่ต้องไม่รวมผลเสียจนเกิดวิกฤตที่สามทางอ้อม

- หลัง event ใหญ่จบ ให้มีช่วงฟื้นตัว/พักอย่างน้อย 1–2 ฤดูกาลเกมก่อนภัยใหญ่ชนิดเดิมกลับมา เว้นแต่สาเหตุในโลกยังไม่ถูกแก้

ค่าจริงปรับตามจำนวนภูมิภาคและความเร็วเวลาโลก

## 4. วงจรชีวิตของ Global Event

Phase 0: เงื่อนไขก่อตัว (Pressure Building)

ความเสี่ยงสะสมจากสภาพโลก แต่ยังไม่แสดงเป็นภัยชัดเจน ตัวอย่างเช่น ฝนตกน้อยกว่าปกติ คลังอาหารเริ่มลด หรือข่าวสัตว์ย้ายถิ่น

Phase 1: สัญญาณเตือน (Telegraph)

ระยะตั้งต้นสำหรับออนไลน์: **12–48 ชั่วโมงจริง** สำหรับภัยใหญ่ หรือกำหนดเป็นช่วงโลกที่เทียบเท่า

- เผยสัญญาณบางส่วนและระดับความเชื่อมั่น

- NPC เริ่มพูดคุย ประเมิน และเสนอทางเลือก

- กลุ่มดาวสามารถส่งลาง/เปิดข้อมูล/ชี้เป้าสนับสนุน

- ยังไม่เกิดผลเสียสูงสุด

- ผู้เล่นที่ออฟไลน์ยังมีเวลาตามสรุปย้อนหลัง

Phase 2: ผลกระทบเริ่มต้น (Onset)

ผลกระทบชัดขึ้น เช่น ผลผลิตลด เส้นทางไม่ปลอดภัย หรือความต้องการยาสูงขึ้น ระบบเปิดเป้าหมายตอบสนองหลายทาง

Phase 3: วิกฤต (Crisis)

เกิดจุดตัดสินใจสำคัญ เช่น ต้องเลือกระหว่างแบ่งอาหาร ย้ายประชากร หรือลงทุนป้องกัน เป็นช่วงที่ผลของการเตรียมตัว/การร่วมมือปรากฏ

Phase 4: คลี่คลาย (Resolution)

Event จบด้วยหนึ่งในหลายผลลัพธ์ เช่น ยับยั้งได้ คลี่คลายบางส่วน เปลี่ยนเป็นปัญหาระยะยาว หรือเกิดความสูญเสียที่มีเหตุผล

Phase 5: ฟื้นฟูและมรดก (Recovery & Legacy)

หลังเหตุการณ์ ระบบติดตามหนี้สิน ทรัพยากรที่ใช้ ความไว้ใจ การย้ายถิ่น การสืบทอด และการเปลี่ยนนโยบาย สรุปผลลงพงศาวดาร

กติกาเรื่องเวลา

- Event ออนไลน์ต้องไม่ใช้หน้าต่างตอบสนองสั้นจนคนที่ไม่ได้ล็อกอินพลาดโดยไม่มีทางเลือก

- การพลาดช่วง telegraph ไม่ทำให้เสียสิทธิ์ทุกอย่าง ผู้เล่นยังร่วมในช่วง crisis/recovery ได้

- NPC ดำเนินการต่อเมื่อไม่มีผู้เล่นตอบสนอง

- ช่วงเวลาทั้งหมดผูกกับ world clock/เวลาจริงตามการตั้งค่าเซิร์ฟเวอร์ และต้องแสดงใน UI

## 6. การประเมินความรุนแรงและการสเกล

### 6.1 ตัวแปรความรุนแรง

ความรุนแรงตั้งจากความเปราะบางของพื้นที่และสาเหตุ ไม่ตั้งจากจำนวนผู้เล่น:

> severity = hazard_intensity × exposure × vulnerability
>
> × (1 - preparedness_factor)

- <u>hazard_intensity</u>: ความแรงของภัย

- <u>exposure</u>: จำนวนคน/สินค้า/โครงสร้างพื้นฐานที่ได้รับผล

- <u>vulnerability</u>: ความเปราะบาง เช่น ขาดคลังสำรองหรือทางเลือกเส้นทาง

- <u>preparedness_factor</u>: ความพร้อมที่สะสมจากโครงสร้างพื้นฐาน/แผนก่อนหน้า

### 6.2 ห้ามสเกลตามจำนวนกลุ่มดาวตรง ๆ

การเพิ่มผู้เล่นไม่ได้เพิ่มจำนวนมอนสเตอร์หรือขนาดภัยโดยอัตโนมัติ เพราะจะทำให้ความร่วมมือไม่มีวันเก่งขึ้น เป้าหมายคือ:

- NPC และสถาบันเป็นฐานการรับมือ

- กลุ่มดาวเปลี่ยนความเสี่ยง/คุณภาพการตอบสนองได้ภายใต้เพดาน

- หากมีผู้เล่นมาก ผลสนับสนุนรวมมี diminishing returns

- event อาจมีเป้าหมายย่อยหลายพื้นที่ให้ช่วย แต่ไม่เพิ่ม health pool อย่างไร้เหตุผล

### 6.3 ผลลัพธ์หลายมิติ

อย่าตัดสิน event ด้วยค่าเดียว เช่น “แถบ progress เต็ม = ชนะ” ติดตามอย่างน้อย:

- **ความเสียหาย/การสูญเสีย:** สินค้า อาคาร บาดเจ็บ และการหยุดงาน

- **ความต่อเนื่อง:** บริการ/การค้า/อาหาร/ยา ยังดำเนินได้หรือไม่

- **ความเป็นธรรม:** กลุ่มใดรับภาระมากเกินไปหรือถูกละเลย

- **ความร่วมมือ:** ความไว้ใจระหว่างชุมชน/องค์กรเปลี่ยนอย่างไร

- **ความยืดหยุ่น:** มีระบบ/ความรู้ใหม่ช่วยรับมือครั้งหน้าไหม

- **ต้นทุนฟื้นฟู:** หนี้ งบ และเวลาที่ต้องใช้

## 7. บทบาทของ NPC และองค์กรในการรับมือ

### 7.1 NPC ตอบสนองตามอาชีพและแรงจูงใจ

- เกษตรกรเก็บเกี่ยวก่อนเวลา/เปลี่ยนชนิดพืช/ช่วยคลังชุมชน

- พ่อค้าเลือกเส้นทางใหม่หรือชะลอการเดินทาง

- ผู้รักษาจัดลำดับผู้ป่วยตามความเร่งด่วนและยาในสต็อก

- นักผจญภัยรับภารกิจที่สอดคล้องกับทักษะ/ความเสี่ยง

- ผู้นำชุมชนแบ่งงบและจัดลำดับบริการ

- ครัวเรือนเลือกย้ายถิ่น/ประหยัด/ขอความช่วยเหลือ

### 7.2 องค์กรและ Factions

แต่ละองค์กรประเมิน event จากประโยชน์/ความเสียหายต่อสมาชิก:

- กิลด์อาจเสนอภารกิจและจัดทรัพยากร

- พ่อค้าร่วมลงทุนขบวนสินค้า หากเส้นทางกลับมาคุ้ม

- Faction อาจสนับสนุนนโยบายหนึ่งและคัดค้านอีกนโยบาย

- รัฐ/สภาอาจใช้คลังสำรอง เพิ่มงบยาม หรือเก็บภาษีฉุกเฉิน

การช่วยเหลือมีต้นทุนและอาจเกิดความขัดแย้งจริง เช่น การใช้เงินซ่อมสะพานอาจเลื่อนการสร้างคลังยา

### 7.3 เกณฑ์การตัดสินใจองค์กร

องค์กรเลือก action ด้วย Utility ที่รวม:

> organization_utility = member_benefit
>
> \+ legitimacy_gain
>
> \+ long_term_resilience
>
> \- budget_cost
>
> \- political_backlash
>
> \- opportunity_cost

องค์กรไม่มีทรัพยากร/แรงงานไม่จำกัด และไม่รู้ข้อมูลที่ยังไม่ถูกส่งถึง

## 8. บทบาทของกลุ่มดาวในการรับมือ

กลุ่มดาวเป็น **ตัวเร่ง/ผู้สนับสนุน** ไม่ใช่กลไกหลักเพียงอย่างเดียวของการรอดชีวิต

### 8.1 บทบาทที่ทำได้

- **ผู้สังเกต:** ใช้พยากรณ์/ติดตามสัญญาณ

- **ผู้ชี้ทาง:** ส่งลาง/แบ่งปันข้อมูลที่ปลดล็อกได้

- **ผู้ระดมกำลังใจ:** พรหรือแรงบันดาลใจต่อปาร์ตี้/ชุมชน

- **ผู้พิทักษ์:** ลดผลเสียหรือช่วยถอนตัว

- **ผู้เชื่อมโยง:** สนับสนุนการร่วมมือขององค์กร/ชุมชนผ่าน event ที่อนุญาต

### 8.2 ข้อจำกัด

- ใช้เพดานอิทธิพลและคูลดาวน์ของระบบเดิม

- แต้มที่ใช้ต่อ event ต่อกลุ่มดาวมีเพดาน

- ผลรวมข้ามกลุ่มดาวมี diminishing returns และ cap ตามหมวด

- ไม่มีอิทธิพลร่วมที่หัวหน้าวงถอนใช้ได้เอง

- ไม่มีพลังสร้างอาหาร เงิน แรงงาน หรือประชากรจากศูนย์

- หากไม่มีผู้เล่นเข้าร่วม NPC ยังรับมือได้ แต่อาจเสียหายมากกว่า

### 8.3 เป้าหมายร่วมของกลุ่มดาว

เหตุการณ์หนึ่งอาจมีเป้าหมายหลายด้าน เช่น:

- รักษาเสบียงขั้นต่ำ

- เปิดเส้นทางการค้าอย่างน้อยหนึ่งเส้น

- ลดการบาดเจ็บของประชากร

- รักษาความร่วมมือระหว่างชุมชน

- เก็บข้อมูล/สร้างแผนป้องกันภัยครั้งต่อไป

กลุ่มดาวเลือกช่วยเป้าหมายย่อยต่างกันได้ โดยไม่มีระบบ “ฝ่ายชนะ” เพียงฝ่ายเดียว

## 9. ตัวอย่าง Global Event: ภัยแล้งและคลังอาหารตึงตัว

สาเหตุและสัญญาณเตือน

- ฝนต่ำกว่าค่าฤดูกาลหลายรอบ

- ระดับน้ำและผลผลิตลดลง

- พ่อค้ารายงานราคาธัญพืชจากพื้นที่รอบนอกสูงขึ้น

- คลังหมู่บ้านเหลืออาหารสำรองต่ำกว่าเป้าหมาย

ระยะที่ 1 — ข่าวเตือน

ผู้เล่นเห็นสัญญาณ “เสี่ยงภัยแล้ง — ความเชื่อมั่นปานกลาง” เกษตรกรประเมินว่าจะเร่งเก็บเกี่ยวหรือเก็บเมล็ดไว้ปลูก ผู้นำชุมชนตรวจคลังและสภาเมืองพิจารณานำเข้า

ทางเลือก:

- ส่งลางเพื่อเปิดเผยเส้นทางแหล่งน้ำ/เมล็ดสำรอง

- สนับสนุนการกักตุนคลังชุมชน

- ช่วยพ่อค้าคำนวณเส้นทางนำเข้า

- ไม่แทรกแซงและปล่อยให้ชุมชนดำเนินตามข้อมูลที่มี

ระยะที่ 2 — ผลผลิตลด

- ราคาธัญพืชเริ่มเพิ่มตามสูตร แต่ไม่เกินเพดานรายวัน

- ครัวเรือนเปลี่ยนไปใช้สินค้าทดแทน

- กิลด์อาจรับงานคุ้มกันขบวนอาหาร

- เกิดความเห็นต่างระหว่างส่งออกเพื่อหาเงินกับเก็บไว้บริโภค

ระยะที่ 3 — จุดแตกหัก

ชุมชนเลือกหนึ่งหรือผสมหลายทาง:

1. ปันส่วนอาหารตามครัวเรือน

2. นำเข้าโดยใช้งบคลังเมือง

3. ย้ายประชากรบางส่วนชั่วคราว

4. ใช้เมล็ดสำรองลดผลผลิตฤดูถัดไป

5. ส่งผู้เชี่ยวชาญสร้างบ่อ/ระบบชลประทาน

ผลลัพธ์

- **ยับยั้งได้ดี:** คลังไม่หมด แต่เกิดหนี้/โครงการน้ำที่ต้องซ่อมบำรุง

- **ประคองได้:** อาหารพอขั้นต่ำ แต่ราคาสูงและขวัญกำลังใจลด

- **ล้มเหลวบางส่วน:** ครัวเรือนบางส่วนย้ายถิ่น การผลิตปีถัดไปลด และเกิดความขัดแย้งเรื่องการปันส่วน

- **วิกฤต:** เกิดจากการขาดการเตรียม/เส้นทางขาดต่อเนื่อง มีความสูญเสียและผลระยะยาว แต่มีเส้นทางฟื้นฟู ไม่ปิดแคมเปญ

สิ่งที่ระบบทดสอบ

- การผลิตเกษตรและสต็อกคลัง

- ราคาและสินค้าทดแทน

- การค้าระหว่างพื้นที่และความเสี่ยงขนส่ง

- งบรัฐ/กิลด์และการจัดสรร

- ความเป็นธรรมและความไว้ใจในชุมชน

- การย้ายถิ่น/ผลต่อครัวเรือนและรุ่นถัดไป

## 10. ตัวอย่าง Global Event: ฝูงมอนสเตอร์ย้ายถิ่น

สาเหตุ

- แหล่งอาหาร/ถิ่นอาศัยถูกทำลาย

- มอนสเตอร์ในพื้นที่เดิมมีจำนวนมาก

- เส้นทางอพยพถูกปิดหรือฤดูกาลเปลี่ยน

ผลกระทบข้ามระบบ

- เส้นทางการค้าบางส่วนเสี่ยงขึ้น

- คนเก็บของ/เกษตรกรหยุดเข้าเขตชายป่า

- สินค้าหนัง/สมุนไพรขาดตลาด

- กิลด์รับงานลาดตระเวนและคุ้มกัน

- หน่วยยามต้องเลือกระหว่างป้องกันเมืองหรือช่วยขบวน

- Faction อาจเห็นต่างว่าควรกำจัดฝูงหรือเปิดเส้นทางอพยพให้

ทางรับมือ

- ทำแนวป้องกัน/อพยพคน

- คุ้มกันขบวนและหลีกเลี่ยงเส้นทาง

- สืบหาสาเหตุ/ย้ายแหล่งอาหารของฝูง

- ปราบเฉพาะผู้นำฝูงหรือรังหลัก

- เจรจา/จัดพื้นที่กันชน หากประเภทมอนสเตอร์รองรับ

ระบบไม่ควรให้ผลลัพธ์ทั้งหมดขึ้นกับการฆ่ามอนสเตอร์ เพราะต้องทดสอบการค้า การทูต การอพยพ และการจัดสรรงบด้วย

## 11. ตัวอย่าง Global Event: โรคพืชในพื้นที่เกษตร

เป็นภัยต่อระบบอาหารและองค์ความรู้ ไม่ใช่ภัยต่อสู้โดยตรง

- สัญญาณเริ่มจากผลผลิตบางชนิดลด/มีอาการผิดปกติ

- ข่าวสารอาจคลาดเคลื่อน ทำให้บางชุมชนเชื่อว่าเป็นสภาพอากาศหรือแมลง

- ทางเลือก: แยกแปลง ทดลองเมล็ดใหม่ ส่งตัวอย่างให้ผู้เชี่ยวชาญ ลดการปลูกชนิดเดียว หรือขอเมล็ดจากภูมิภาคอื่น

- ผลสำเร็จอาจแลกกับการผลิตลดชั่วคราวและต้นทุนศึกษา

- ผลล้มเหลวบางส่วนทำให้ราคาอาหารเปลี่ยน สร้างภาระคลังและการย้ายแรงงาน

- ความรู้ที่ค้นพบถูกบันทึกและถ่ายทอดสู่รุ่นถัดไป จึงเชื่อมกับ Generation & Legacy

## 12. ระบบเป้าหมายและการคืบหน้า

แต่ละ event มี progress tracks 2–4 เส้น ไม่ใช่ progress bar เดียว

ตัวอย่างภัยแล้ง:

- <u>food_reserve</u> — รักษาอาหารสำรอง

- <u>trade_access</u> — เปิดทางนำเข้า

- <u>community_cohesion</u> — รักษาความร่วมมือและความเป็นธรรม

- <u>future_resilience</u> — เพิ่มความพร้อมฤดูถัดไป

ค่าติดตามอาจเป็น 0–100 แต่ UI แสดงระดับ/แนวโน้ม พร้อมแหล่งที่เปลี่ยนค่า เช่น “คลังสำรองเพิ่ม 8 หน่วยจากการนำเข้า”

การประเมินผลลัพธ์

> outcome_score = weighted_sum(track_scores)
>
> \+ preparedness_bonus
>
> \+ npc_institution_response
>
> \+ bounded_constellation_effect
>
> \- unresolved_costs

ผลสรุปมีหลายระดับ แต่แสดง breakdown ว่าอะไรช่วย/อะไรขาด ไม่ทำให้คะแนนลับเป็นคำตัดสินที่ผู้เล่นตรวจสอบไม่ได้

## 13. การจัดสรรความช่วยเหลือและความเป็นธรรม

- พิจารณาความจำเป็นของชุมชน ไม่ใช่จำนวนกลุ่มดาวที่สนับสนุนอย่างเดียว

- ประชากรเปราะบาง/พื้นที่ขาดแคลนควรมีน้ำหนักในแผนของ NPC แต่ไม่ใช้เป็น “โบนัสคะแนน” ซ่อนเร้น

- หากรัฐ/กิลด์แบ่งทรัพยากรไม่เท่ากัน ให้แสดงเหตุผลและผลต่อความชอบธรรม

- กลุ่มดาวอาจสนับสนุนชุมชนที่ถูกละเลย แต่ผลรวมยังมีเพดาน

- ไม่มีการจัดอันดับ “ผู้บริจาคมากสุด” ที่ชักจูงให้ผู้เล่นแย่งกันใช้พลัง

ระบบสามารถมีปัญหาความเป็นธรรมในเรื่องราว แต่ต้องทำให้ผู้เล่นอ่านออกและมีทางตอบสนองในอนาคต

## 14. ความล้มเหลวและการฟื้นตัว

### 14.1 ความล้มเหลวไม่ใช่จบเกม

ผลลัพธ์แย่เปิด “สถานะฟื้นฟู”:

- มีเป้าหมายซ่อมแซม/นำเข้า/ฝึกคน

- หนี้ชุมชนมีเพดานและแผนชำระ

- องค์กรอาจเสียชื่อเสียงหรือเปลี่ยนผู้นำ

- ครัวเรือนอาจย้ายถิ่น แต่ยังมีการติดต่อ/กลับมาได้ตามเรื่อง

- ความรู้จากความผิดพลาดถูกบันทึก

### 14.2 ฟื้นฟูต้องใช้ทรัพยากรจริง

การฟื้นฟูใช้เงิน วัตถุดิบ แรงงาน หรือเวลา แต่มีทางเลือกหลายระดับ เช่น ซ่อมจุดสำคัญก่อน สร้างบริการชั่วคราว หรือลดมาตรฐานเพื่อประคองสถานการณ์

### 14.3 หลีกเลี่ยงวงจรพังถาวร

หากชุมชนไม่มีอาหารและไม่มีเงินซื้อ ระบบต้องมี safety valve ที่มองเห็นได้ เช่น คลังเมืองปล่อยสำรองหรือชุมชนย้ายแรงงาน แต่ให้บันทึกต้นทุน/ผลข้างเคียง ไม่สร้างความช่วยเหลือไร้ที่มา

## 15. รางวัลและความก้าวหน้าจาก Global Events

รางวัลของกลุ่มดาวเน้นการยอมรับและประวัติศาสตร์ ไม่เพิ่มกำลังแข่งขันถาวร:

- ชื่อ/สัญลักษณ์ในพงศาวดาร (เลือกเปิดเผยได้)

- ฉายาหรือ cosmetic ตามบทบาทที่ช่วย

- การปลดล็อกข้อมูลประวัติศาสตร์/เหตุการณ์เบื้องหลัง

- คะแนนชื่อเสียงที่ใช้กับของตกแต่ง/เป้าหมายเรื่องราว ไม่ใช่อิทธิพล

- NPC/ชุมชนอาจจดจำการช่วยเหลือ แต่ไม่กลายเป็นผู้ติดตามถาวร

รางวัลที่สำคัญที่สุดคือโลกเปลี่ยนตามเหตุการณ์ เช่น เส้นทางปลอดภัยขึ้น มีคลังใหม่ หรือเกิดประเพณีรำลึก ไม่ใช่ของส่วนตัวที่ผู้เล่นคนอื่นมองไม่เห็น

## 16. ระบบสุ่มและความหลากหลาย

### 16.1 ใช้ event archetype + modifier

แทนสร้างภัยใหม่ทุกครั้งจากศูนย์ ใช้ archetype ที่ทดสอบได้ เช่น ภัยแล้ง ฝูงมอนสเตอร์ โรคพืช วิกฤตเส้นทาง แล้วสุ่ม modifier:

- พื้นที่และฤดูกาล

- ความรุนแรง/ระยะเวลาสัญญาณเตือน

- องค์กรที่มีความพร้อม/ขัดแย้ง

- ทางเลือกตอบสนองและผลระยะยาว

- ข่าวสารที่ขาด/คลาดเคลื่อน

### 16.2 Seed และความเที่ยงตรง

- ใช้ seed ต่อโลกและ event

- บันทึก <u>world_rule_version</u> และปัจจัยตัดสิน

- ผลสุ่มตัดสินบนเซิร์ฟเวอร์

- ผู้เล่นไม่สามารถรีโหลดเพื่อสุ่มใหม่

- การสุ่มไม่เปลี่ยนกฎความเป็นธรรม/เพดานการสนับสนุน

### 16.3 Anti-repeat

- จำกัด event archetype ซ้ำในพื้นที่เดียวกัน

- หากภัยเดิมกลับมา ต้องมีสาเหตุว่าทำไมปัญหายังไม่ถูกแก้

- เปลี่ยนผล/ผู้ได้รับผล/วิธีรับมือเพื่อไม่ให้กลายเป็นกิจวัตรซ้ำ

- ให้เหตุการณ์ก่อนหน้าสร้างความพร้อม เช่น คลังที่สร้างจากภัยแล้งช่วยลดผลในอนาคต

## 17. UI สำหรับ Global Event

หน้าต่าง Event ควรมี 5 ส่วน:

1. **หัวเรื่องและ phase:** สัญญาณเตือน / ผลกระทบ / วิกฤต / ฟื้นฟู

2. **สิ่งที่รู้:** ข้อเท็จจริง ข่าวลือ และระดับความเชื่อมั่น

3. **ผลกระทบที่กำลังเกิด:** พื้นที่ ประชากร สินค้า และองค์กร

4. **แนวทางรับมือ:** หลายทางเลือกพร้อมต้นทุนและผลแลกเปลี่ยน

5. **การร่วมมือ:** สถานะ NPC/องค์กร/กลุ่มดาว และสิ่งที่ยังขาด

แสดงการมีส่วนร่วม

- “NPC/กิลด์เริ่มนำอาหารสำรองออกมาใช้”

- “กลุ่มดาว 4 ดวงสนับสนุนข้อมูลเส้นทาง”

- “ยังไม่มีการสนับสนุนด้านการคุ้มกัน”

- “การสนับสนุนกำลังใจใกล้เพดานแล้ว; การช่วยเหลืออีกครั้งอาจคุ้มกว่าในหมวดอื่น”

ไม่ใช้ข้อความ “ทุกคนกำลังรอคุณ” เว้นแต่เป็นเหตุการณ์ที่ NPC ตั้งใจส่งคำขอถึงตัวละคร/ชุมชนนั้นจริง

## 18. การทดสอบระบบใน Simulation และ Playtest

Simulation tests

รันหลาย seed และหลายระดับการเข้าร่วม:

- ไม่มีผู้เล่นสนับสนุน

- ผู้เล่น 1–5 คนสนับสนุนกระจายหมวด

- ผู้เล่นจำนวนมากสนับสนุนเป้าหมายเดียว

- สนับสนุนขัดแย้งกันคนละทาง

- NPC/กิลด์มีทรัพยากรสูงและต่ำ

- เส้นทางขาด/คลังสำรองต่ำ/ผู้นำไม่มีความชอบธรรม

ตรวจว่า:

- ไม่มี event สองชุดทำลายระบบเศรษฐกิจพร้อมกันโดยไร้โอกาสรับมือ

- ความเสียหายเพิ่มตามความเปราะบาง/การเตรียมตัว ไม่ใช่จำนวนผู้เล่น

- ไม่มีพลังกลุ่มดาวทำให้ outcome แน่นอน

- NPC มีการตอบสนองแม้ผู้เล่นไม่อยู่

- เงิน/สินค้าและความสัมพันธ์มีเหตุผลใน ledger/chronicle

- หลัง event โลกมี recovery path

Playtest questions

1. ผู้เล่นเห็นสัญญาณเตือนก่อนผลเสียหนักหรือไม่?

2. มีทางช่วยหลายแบบหรือทุกคนรู้สึกว่าต้องใช้พลังชนิดเดียว?

3. ผู้เล่นออฟไลน์รู้สึกว่าถูกลงโทษหรือไม่?

4. ผู้เล่นเข้าใจว่าการช่วยของตนส่งผลตรงไหน?

5. ผลลัพธ์ที่ไม่สมบูรณ์ยังน่าสนใจและอยากเล่นต่อหรือไม่?

6. วิกฤตทำให้ระบบเศรษฐกิจ/สังคมที่ออกแบบไว้ถูกนำมาใช้จริงหรือไม่?

## 19. ขอบเขต MVP ของ Global Events

สร้างก่อน

- Event Director ที่ใช้ world condition และ cooldown

- 3 archetype: ภัยแล้ง/ขาดแคลน, ฝูงมอนสเตอร์ย้ายถิ่น, วิกฤตเส้นทางการค้า

- แต่ละ event มี telegraph, onset, crisis, resolution, recovery

- มีอย่างน้อย 3 แนวทางตอบสนองต่อ event

- NPC/กิลด์/รัฐมี action อัตโนมัติและใช้บัญชีทรัพยากรจริง

- กลุ่มดาวช่วยได้ตามระบบอิทธิพลเดิมและมีเพดานรวม

- event log, ledger references และ chronicle summary

ยังไม่สร้าง

- ภัยที่ฆ่าประชากรเป็นจำนวนมากโดยไม่มีทางตอบสนอง

- Global event ที่ต้องล็อกอิน/กดพร้อมกันในเวลาจำกัด

- สงครามโลกหลายฝ่าย

- Event ที่สเกล HP ตามจำนวนผู้เล่น

- รางวัลอันดับตามการใช้แต้ม/การออนไลน์

- AI สร้างภัยใหม่แบบไร้ขอบเขตโดยไม่มี archetype ที่ผ่านการทดสอบ

## 21. ข้อสรุป

Global Events ควรเป็นบททดสอบว่า **เศรษฐกิจและสังคมของ NPC ทำงานจริงหรือไม่** ไม่ใช่กิจกรรมแยกที่ผู้เล่นเข้ามากดปุ่มร่วมกันเท่านั้น ภัยหนึ่งควรเชื่อมการผลิต การขนส่ง ราคา งบกิลด์ ความชอบธรรม ความสัมพันธ์ และการเติบโตของชุมชน

การออกแบบที่แข็งแรงมีคุณสมบัติ 4 ข้อ:

- มีสาเหตุและสัญญาณเตือน

- มีทางรับมือหลายประเภทและต้นทุนจริง

- โลกดำเนินต่อได้เมื่อไม่มีผู้เล่น

- ทุกผลลัพธ์สร้างเรื่องราว/ความเปลี่ยนแปลงให้โลกจำ

**คำถามพิสูจน์ระบบ:** หากปิดการสนับสนุนจากกลุ่มดาวทั้งหมด NPC และสถาบันยังรับมือภัยได้หรือไม่ และเมื่อกลุ่มดาวเข้าร่วม ผลที่เพิ่มขึ้นชัดเจนแต่ไม่รับประกันชัยชนะหรือไม่?
