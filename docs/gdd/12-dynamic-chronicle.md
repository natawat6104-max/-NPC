# ภาคผนวก GDD: Dynamic Chronicle & History Generation

> **สถานะ (docs/DECISIONS.md):** ✅ ใช้ใน MVP แบบ template อย่างเดียว  
> ถ้าเนื้อหาในไฟล์นี้ขัดกับ [DECISIONS.md](../DECISIONS.md) ให้ยึด DECISIONS.md · ตัวเลขดู [BALANCE.md](../BALANCE.md)

ระบบบันทึกประวัติศาสตร์อัตโนมัติและสร้างเรื่องราวของ NPC

**เกม:** พงศาวดารใต้ดวงดาว  
**บริบท:** โลกออนไลน์ร่วมกัน; NPC เป็นผู้สร้างเหตุการณ์ ผู้เล่นกลุ่มดาวเป็นผู้เฝ้ามอง/ชี้นำ  
**เวอร์ชัน:** 0.1 — ข้อเสนอสำหรับต้นแบบ  
**เป้าหมาย:** แปลงเหตุการณ์จากระบบจำลองให้เป็นประวัติศาสตร์ที่ถูกต้อง อ่านสนุก ค้นย้อนหลังได้ และสะท้อนชีวิตหลายระดับ ตั้งแต่บุคคลจนถึงอารยธรรม

**หลักการ:** Chronicle ไม่แต่งว่าอะไรเกิดขึ้น แต่คัดเลือกและเล่า “ข้อเท็จจริงที่เกิดขึ้นแล้ว” ให้เห็นเหตุ ผล ผู้เกี่ยวข้อง และสิ่งที่เปลี่ยนไป

## 1. เป้าหมายของระบบ

ผู้เล่นควรสามารถ:

1.  เห็นเหตุการณ์สำคัญที่เกิดขึ้นแม้ตนไม่ได้ออนไลน์

2.  เข้าใจว่าเหตุการณ์หนึ่งเกิดจากอะไร ส่งผลกับใคร และต่อยอดไปสู่อะไร

3.  ติดตามเส้นชีวิตของ NPC ปาร์ตี้ ครัวเรือน กิลด์ Faction ชุมชน และอาณาจักร

4.  เห็นเรื่องราวที่เกิดขึ้นเองจากระบบ โดยไม่รู้สึกว่าเป็นข้อความสุ่มไร้หลักฐาน

5.  ย้อนดูเหตุการณ์ตามเวลา/สถานที่/ตัวละคร และแยกข้อเท็จจริงจากข่าวลือได้

6.  อ่านสรุปมหากาพย์ของตัวละครหรือโลก โดยไม่ต้องไล่อ่าน log ทุกบรรทัด

7.  เห็นผลของกลุ่มดาวอย่างโปร่งใส โดยไม่ยกผู้เล่นคนใดเป็นเจ้าของ NPC

สิ่งที่ระบบไม่ควรทำ

- บันทึกทุกการเดินหนึ่งก้าวเป็นเรื่องสำคัญจนพงศาวดารล้น

- สร้างเหตุผล/ผลลัพธ์ที่ไม่ตรงกับสถานะจริงของเกม

- เปิดเผยความลับก่อนมีตัวละครหรือผู้เล่นได้รับข้อมูล

- ทำให้ผู้เล่นต้องอ่านเรื่องยาวเพื่อเข้าใจสถานการณ์ปัจจุบัน

- ปล่อยให้การสร้างข้อความมีอำนาจเปลี่ยนข้อมูลเกม

- ลบประวัติสำคัญเพื่อประหยัดพื้นที่โดยไม่มีการสรุป/เก็บหลักฐาน

## 2. สถาปัตยกรรม: แยกข้อเท็จจริงออกจากการเล่าเรื่อง

ระบบแบ่งเป็น 5 ชั้น:

1.  **Simulation State:** สถานะปัจจุบันของโลก/NPC/เศรษฐกิจ

2.  **Canonical Event Log:** เหตุการณ์เชิงโครงสร้างที่เกิดขึ้นจริง พร้อมเวลาและสาเหตุ

3. **Chronicle Selection:** จัดระดับความสำคัญ รวมเหตุการณ์ซ้ำ และเลือกเหตุการณ์ที่ควรเก็บถาวร

4. **Story Arc Builder:** เชื่อมเหตุการณ์เป็นเส้นเรื่องและสรุปพัฒนาการ

5. **Narrative Renderer:** สร้างหัวข้อ/คำบรรยาย/สรุปจากข้อเท็จจริงที่ถูกเลือก

> World simulation changes
>
> ↓
>
> Structured event + cause/effect references
>
> ↓
>
> Validation and importance scoring
>
> ↓
>
> Deduplicate / aggregate / preserve
>
> ↓
>
> Detect character, community and world arcs
>
> ↓
>
> Render grounded chronicle text
>
> ↓
>
> Index and expose by visibility rules

แหล่งความจริง (Source of Truth)

- สถานะ simulation และ event log เป็นความจริงของระบบ

- ข้อความ Chronicle เป็นชั้นนำเสนอ ไม่แก้สถานะเกม

- หากข้อความขัดกับข้อมูล event ให้ถือข้อมูล event เป็นหลักและ regenerate/แก้ template

- การสรุป AI หรือ template ห้ามสร้างผู้เกี่ยวข้อง ไอเท็ม เหตุผล หรือผลลัพธ์ที่ไม่มีใน event facts

## 3. โครงสร้างข้อมูลของเหตุการณ์

### 3.1 Canonical Event

> ChronicleEvent
>
> \- event_id
>
> \- event_type
>
> \- world_timestamp / game_date / season
>
> \- location_id / region_id
>
> \- participants\[\]: entity_id + role
>
> \- cause_event_ids\[\]
>
> \- facts: structured key-value data
>
> \- immediate_effects\[\]
>
> \- long_term_hooks\[\]
>
> \- knowledge_scope: public / local / faction / private-to-characters
>
> \- known_by\[\] or knowledge_rule
>
> \- importance_score
>
> \- confidence / uncertainty
>
> \- world_rule_version / random_seed_reference
>
> \- source_system: AI / economy / combat / faction / constellation / event_director
>
> \- parent_arc_ids\[\]
>
> \- narrative_status: raw / candidate / chronicle / summarized / archived

### 3.2 Facts ต้องมีความหมายเชิงเกม

ตัวอย่าง event <u>party_returned_from_expedition</u> อาจบันทึก:

> facts:
>
> \- party_id: party_17
>
> \- members_returned: \[rena, toma\]
>
> \- destination: silverroot_forest
>
> \- collected: {moonleaf: 12}
>
> \- injury: {toma: minor}
>
> \- quest_status: success
>
> \- cause_of_route_change: warning_from_constellation

ข้อความสรุปสามารถเปลี่ยนสำนวนได้ แต่ต้องรักษาจำนวน สิ่งของ บุคคล สถานะ และสาเหตุเหล่านี้

### 3.3 Event lineage

ทุกเหตุการณ์สำคัญเชื่อมด้วย <u>cause_event_ids</u> เช่น:

> ฝนต่ำต่อเนื่อง
>
> → ผลผลิตธัญพืชลด
>
> → คลังอาหารต่ำกว่าจุดสำรอง
>
> → สภาเมืองนำเข้าอาหาร
>
> → เส้นทางการค้าถูกคุ้มกัน
>
> → ชุมชนฟื้นตัวแต่มีหนี้เพิ่ม

ผู้เล่นเปิดดูเส้นเหตุ/ผลได้ แต่ไม่จำเป็นต้องเห็นกราฟทั้งหมดในหน้าเดียว

## 4. คัดเลือกเหตุการณ์ให้เป็นประวัติศาสตร์

### 4.1 ระดับการเก็บ

| ระดับ                     | ลักษณะ                                      | วิธีเก็บ                                |
|--------------------------|--------------------------------------------|--------------------------------------|
| **Raw simulation event** | การกระทำย่อยจำนวนมาก เช่น เคลื่อนที่/ซื้อของปกติ    | เก็บชั่วคราวหรือรวมเป็นสถิติ                |
| **Notable event**        | มีผลกับตัวละคร เป้าหมาย ทรัพยากร หรือความสัมพันธ์   | เก็บใน timeline เฉพาะบุคคล/พื้นที่และสรุปได้ |
| **Chronicle event**      | จุดเปลี่ยนสำคัญ เช่น ภารกิจสำเร็จ/ล้มเหลว ผู้นำเปลี่ยน | เก็บถาวรและค้นหาได้                     |
| **Era-defining event**   | เปลี่ยนเมือง อาณาจักร วิกฤตใหญ่ หรือมรดกข้ามรุ่น     | เก็บถาวรแบบห้ามลบ พร้อมสรุปและสายเหตุผล   |

### 4.2 คะแนนความสำคัญ

ใช้คะแนนตั้งต้น 0–100:

> importance = consequence_weight
>
> \+ character_arc_weight
>
> \+ social_or_economic_impact
>
> \+ rarity_or_novelty
>
> \+ relationship_change
>
> \+ player_attention_relevance
>
> \+ long_term_relevance
>
> \- repetition_penalty
>
> \- routine_action_penalty

องค์ประกอบหลัก:

- **ผลกระทบ:** เปลี่ยนสุขภาพ สถานะ ภารกิจ สต็อก ความปลอดภัย หรือบทบาทหรือไม่

- **พัฒนาการตัวละคร:** เปลี่ยนเป้าหมาย ความสัมพันธ์ อาชีพ หรือแนวโน้มหรือไม่

- **ผลระดับสังคม:** กระทบครัวเรือน กิลด์ Faction ชุมชน หรือรัฐหรือไม่

- **ความหายาก:** เหตุการณ์นี้เกิดบ่อยหรือมีเอกลักษณ์

- **ความสนใจผู้เล่น:** เกี่ยวกับ NPC ที่จับตามอง/เหตุการณ์ที่ผู้เล่นมีส่วนหรือไม่

- **ผลระยะยาว:** สร้าง hook ที่ยังดำเนินต่อหรือไม่

ค่าคะแนนนี้ไม่ควรเปิดเป็น “คะแนนคุณค่าของชีวิต NPC” แต่ใช้ภายในเพื่อจัดลำดับและลด spam

### 4.3 Threshold ตั้งต้น

- คะแนนต่ำกว่า 25: ไม่เก็บเป็นเรื่องแยก; รวมในสรุปประจำวัน/สถิติ

- 25–49: เก็บใน timeline ย่อของบุคคล/กิจการ

- 50–74: สร้าง Notable Event พร้อมคำบรรยายสั้น

- 75 ขึ้นไป: เข้า Chronicle หลักของบุคคล/ชุมชน/โลก

- 90 ขึ้นไปหรือมี tag <u>era_defining</u>: เป็นหมุดหมายสำคัญและห้ามถูกยุบรวมจนสูญรายละเอียด

บาง event ถูกกำหนดเป็น Chronicle โดยชนิด เช่น เกิด/เสียชีวิตของ NPC สำคัญ แม้คะแนนคำนวณต่ำกว่ threshold

### 4.4 กันเหตุการณ์ซ้ำ

- รวม event ชนิดเดียวกันที่เกิดถี่ เช่น NPC ซื้ออาหารทุกวัน เป็น daily summary

- ถ้ามีการเปลี่ยนแปลงสำคัญ เช่น ซื้อของชิ้นสุดท้ายจนเกิดขาดแคลน ให้แยกเป็นเหตุการณ์สำคัญ

- ใช้ dedup key: type + actor/organization + location + time window + outcome

- การรวมไม่ลบจำนวนรวม/ผลกระทบ เช่น “ร้านรับซื้อสมุนไพร 8 ครั้ง รวม 32 หน่วย”

- หากเหตุการณ์เดิมมีผลกลับด้านหรือเป็นจุดหักเห ให้สร้าง event ใหม่เชื่อมกับรายการเดิม

## 5. ระบบ Story Arc: เปลี่ยน event ให้เป็นมหากาพย์

Chronicle ไม่ควรสร้างโครงเรื่องจากข้อความอย่างเดียว แต่ใช้ state machine/ตัวตรวจรูปแบบเหตุการณ์เพื่อระบุว่าเส้นเรื่องใดกำลังดำเนิน

### 5.1 ระดับของ Arc

- **Character Arc:** ชีวิต/เป้าหมายของ NPC

- **Relationship Arc:** มิตรภาพ คู่แข่ง ครู–ลูกศิษย์ คู่ชีวิต หรือการแตกหัก

- **Party Arc:** การก่อตั้ง การเดินทาง ความสำเร็จ/แตกกลุ่ม

- **Household/Legacy Arc:** ครัวเรือน การสืบทอด ความรู้/กิจการ

- **Guild/Faction Arc:** การก่อตั้ง เติบโต แตกแยก เปลี่ยนผู้นำ

- **Community Arc:** วิกฤต การฟื้นตัว การลงทุน และความชอบธรรม

- **World/Era Arc:** ภัยใหญ่ การก่อตั้งรัฐ สงคราม/สันติภาพ หรือการเปลี่ยนยุค

### 5.2 โครงสร้าง Arc

> StoryArc
>
> \- arc_id, arc_type, subject_ids\[\]
>
> \- title_seed / theme_tags
>
> \- opened_by_event_id
>
> \- current_stage
>
> \- key_events\[\]
>
> \- unresolved_questions\[\]
>
> \- progress_state
>
> \- last_updated_at
>
> \- resolution_state: ongoing / resolved / abandoned / transformed
>
> \- visibility_scope
>
> \- summary_version

### 5.3 รูปแบบ Arc ที่ตรวจจับได้

ตัวอย่าง “ก้าวสู่การเป็นวีรบุรุษ”:

1. ตัวละครมีเป้าหมายหรือความขาดแคลน

2. รับความเสี่ยง/เริ่มภารกิจ

3. พบอุปสรรคหรือความล้มเหลว

4. ตัดสินใจที่สะท้อนบุคลิก/ความสัมพันธ์

5. ผลลัพธ์เปลี่ยนชื่อเสียง ความสามารถ หรือชุมชน

6. เปิดบทต่อ เช่น เป็นครู/ผู้นำ/คู่แข่ง

Arc ไม่จำเป็นต้องจบสำเร็จ ความล้มเหลว/การเลิกเป้าหมายอาจเป็นบทสรุปที่สมบูรณ์ได้

### 5.4 Arc ไม่บังคับให้ระบบเขียนบท

Arc Builder ตรวจจับรูปแบบจาก event ที่เกิดแล้วและสร้างหัวเรื่อง/สรุป ไม่สร้างเหตุการณ์ใหม่เพื่อให้โครงเรื่องครบสูตร หากไม่มี obstacle หรือ resolution จริง ระบบไม่ควรแต่งเติม

### 5.5 หลาย Arc เชื่อมกันได้

ตัวอย่าง:

- ภัยแล้งของชุมชนเชื่อมกับ arc ของเกษตรกร ผู้รักษา พ่อค้า กิลด์ และสภาเมือง

- การตายของนักผจญภัยเปิด arc ของผู้สืบทอด/สมาชิกปาร์ตี้/กิจการที่เขาทิ้งไว้

- การสร้างสะพานเชื่อม arc เศรษฐกิจและความสัมพันธ์ระหว่างชุมชน

UI แสดงความเชื่อมโยงเป็น “เรื่องนี้เกี่ยวข้องกับ…” พร้อมจำนวน arc ที่เชื่อม แต่ไม่เปิดทุก graph พร้อมกัน

## 6. การสร้างคำบรรยายและสรุป

### 6.1 ลำดับการสร้างข้อความ

1. อ่าน canonical event และ facts ที่ได้รับอนุญาต

2. เลือก template ตาม event type/ระดับความสำคัญ

3. เติมชื่อ เวลา สถานที่ จำนวน และสาเหตุจากข้อมูลจริง

4. ตรวจ consistency: ผู้เกี่ยวข้อง ผลลัพธ์ ไอเท็ม และเวลา

5. สร้างข้อความสั้น/ยาว/หัวเรื่อง

6. เก็บเวอร์ชัน template และ hash ของ facts เพื่อ regenerate ได้

### 6.2 รูปแบบข้อความหลายชั้น

ทุกเหตุการณ์ควรมี:

- **หัวเรื่อง:** สั้นและชี้ผล เช่น “เรน่าพาปาร์ตี้กลับจากป่าพร้อมสมุนไพร”

- **สรุปหนึ่งบรรทัด:** บอกว่าเกิดอะไรและผลหลัก

- **รายละเอียด:** ผู้เกี่ยวข้อง เหตุผล และต้นทุน

- **ผลต่อเนื่อง:** สถานะที่เปลี่ยน/เรื่องที่ยังไม่จบ

- **หลักฐาน/ที่มา:** ลิงก์ไป event facts หรือเหตุการณ์ก่อนหน้า

### 6.3 สำนวนตามบริบท

- Chronicle ทางการ: เป็นกลางและยึดข้อเท็จจริง

- บันทึกส่วนตัว: สรุปผ่านมุมมองสิ่งที่ตัวละครรู้/จำ

- ข่าวลือ: ระบุแหล่งที่มาและความเชื่อมั่น; อาจคลาดเคลื่อน

- คำเล่าขาน: เป็นเวอร์ชันที่สังคมเล่าต่อ ไม่เท่ากับข้อเท็จจริง

อย่าใช้สำนวนเดียวกันกับทุกประเภท เช่น การเสียชีวิตไม่ควรถูกเล่าแบบโฆษณาภารกิจ

### 6.4 LLM เป็นทางเลือก ไม่ใช่ผู้ตัดสิน

หากในอนาคตใช้โมเดลสร้างสำนวน ให้ส่งเฉพาะ facts ที่อนุญาตและกำหนด schema ผลลัพธ์ จากนั้นตรวจทุก entity/date/quantity/outcome กับ canonical event หากตรวจไม่ผ่านให้ fallback ไป template

LLM ไม่มีสิทธิ์:

- เปลี่ยนสถานะเกม

- สร้างของรางวัล/ผู้เสียชีวิต/ความสัมพันธ์ใหม่

- เปิดเผยข้อมูล private/ยังไม่รู้

- ตัดสินว่าใครถูก/ผิดในข้อพิพาท

ต้นแบบสามารถทำ Chronicle ทั้งหมดด้วย template เพื่อให้คงเสถียรและประหยัดทรัพยากร

## 7. มุมมองย้อนดูประวัติศาสตร์

### 7.1 หน้าหลัก Chronicle

ตัวกรอง:

- โลก/ยุค

- ตัวละคร

- ปาร์ตี้

- ครัวเรือน/สายรุ่น

- กิลด์/Faction/รัฐ

- สถานที่

- ประเภทเหตุการณ์

- ช่วงเวลา

- เหตุการณ์ที่ผู้เล่น/กลุ่มดาวมีส่วน

### 7.2 Timeline

- เรียงตามเวลาและแสดงหมุดเหตุการณ์สำคัญ

- ซูมจากระดับวัน → ฤดูกาล → ปี/ยุค

- เมื่อซูมออก รวมเหตุการณ์ย่อยเป็นสรุป

- เมื่อซูมเข้า แสดงลำดับเหตุการณ์และความสัมพันธ์เชิงสาเหตุ

- มีปุ่ม “กลับสู่ปัจจุบัน” ชัดเจน

การย้อนดูเป็นเพียงการอ่านข้อมูล ไม่ย้อนเวลา ไม่แก้ผลโลก และไม่หยุดเซิร์ฟเวอร์

### 7.3 มุมมองชีวประวัติ NPC

ประกอบด้วย:

1. สรุปชีวิตปัจจุบัน/สถานะ

2. เป้าหมายสำคัญที่เคยมี

3. 3–7 หมุดเหตุการณ์ที่นิยามชีวิต

4. ความสัมพันธ์ที่เปลี่ยนแปลงสำคัญ

5. บทบาทในปาร์ตี้/กิลด์/ชุมชน

6. Legacy ที่ส่งต่อให้คนรุ่นหลัง

7. เรื่องที่ยังค้าง/Arc ที่ยังไม่จบ

### 7.4 มุมมองประวัติศาสตร์โลก

แสดงยุค/บทและเหตุการณ์ระดับใหญ่:

- วิกฤตและผลลัพธ์

- การเปลี่ยนแปลงเศรษฐกิจ/อำนาจ

- การตั้งหรือแตกองค์กร/อาณาจักร

- การย้ายถิ่น/การเปลี่ยนประชากร

- จุดเปลี่ยนที่เกิดจาก NPC และการสนับสนุนกลุ่มดาว

### 7.5 การค้นหา

ค้นด้วยชื่อ/สถานที่/องค์กร/ประเภทเหตุการณ์ และคำสำคัญที่ระบบจัด index เช่น “ภัยแล้ง”, “ผู้สืบทอด”, “เส้นทางการค้า” ผลค้นหาต้องเคารพสิทธิ์การมองเห็นและไม่คืนเหตุการณ์ลับให้ผู้ที่ยังไม่รู้

## 8. สิทธิ์การมองเห็นและความรู้

### 8.1 ชั้นข้อมูล

1. **Canonical truth:** ข้อเท็จจริงในเซิร์ฟเวอร์ ใช้ตรวจสอบ simulation

2. **Public chronicle:** เหตุการณ์ที่สาธารณะ/ชุมชนรับรู้

3. **Local account:** ข่าวที่รู้เฉพาะพื้นที่/องค์กร

4. **Character memory:** สิ่งที่ NPC แต่ละคนจำและตีความ

5. **Player record:** ข้อมูลส่วนตัว เช่น watchlist และโน้ตผู้เล่น

### 8.2 การเปิดเผยตามเวลา

เหตุการณ์อาจเกิดก่อนที่ผู้เล่น/ชุมชนจะรู้ ระบบแสดงได้เป็น:

- “เหตุการณ์ที่บันทึกแล้ว” หากเป็นข้อมูลสาธารณะ

- “มีข่าวลือ…” หากเพิ่งมาถึงและยังไม่ยืนยัน

- “ข้อมูลถูกปิดไว้” หากเป็นความลับตามเนื้อเรื่อง

เมื่อความจริงเปิดเผย ให้เชื่อมข่าวลือเดิมกับ canonical event แทนการลบประวัติข่าวลือ

### 8.3 Attribution ของกลุ่มดาว

- บันทึกภายในว่า intervention ใดมีผลต่อ event

- เปิดชื่อผู้สนับสนุนต่อสาธารณะเมื่อผู้เล่นเลือก opt-in หรือระบบเป็นกิจกรรมสาธารณะตามกติกา

- สามารถแสดงหมวดผลโดยไม่เปิดชื่อ เช่น “มีการสนับสนุนด้านป้องกัน”

- ห้ามกล่าวเกินจริงว่า “กลุ่มดาว X ช่วยชีวิต NPC” หากความสำเร็จมาจากหลายปัจจัย

## 9. การสรุปอัตโนมัติและการสร้างมหากาพย์

### 9.1 Daily/Seasonal digest

- **สรุปรายวัน:** 3–5 เหตุการณ์ที่สำคัญต่อผู้เล่น/โลก

- **สรุปรายฤดูกาล:** วิกฤตที่เกิด สถานะเศรษฐกิจ การเปลี่ยนผู้นำ และตัวละครที่เติบโต

- **สรุปบท/ปี:** ผลของเป้าหมายหลัก เรื่องที่จบ/ยังค้าง และผลต่อรุ่นถัดไป

การสรุปไม่ควรเป็นการเลือก event ที่มีคะแนนสูงที่สุดอย่างเดียว ต้องกระจายความสนใจระหว่างบุคคล พื้นที่ และระบบสังคม

### 9.2 Story significance ไม่เท่ากับความนิยม

ป้องกันไม่ให้ NPC ที่ผู้เล่นจำนวนมากจับตามองกลืนเรื่องราวทั้งหมด:

- มีพื้นที่ขั้นต่ำใน digest ให้ชุมชน/องค์กร/ตัวละครรอง

- ใช้ความสำคัญต่อโลกและความใหม่ ไม่ใช้จำนวน watchlist เป็นน้ำหนักเดียว

- ไม่เปลี่ยนความจริงของประวัติศาสตร์ตามจำนวนผู้เล่น

- ให้ผู้เล่นเลือก personalized digest ได้ แต่ Chronicle โลกยังคงเป็นมาตรฐานเดียวกัน

### 9.3 สรุปมหากาพย์ (Epic Summary)

เมื่อ Arc ปิดหรือถึงหมุดหมายสำคัญ สร้างเรื่องย่อที่มีโครง:

- **จุดเริ่ม:** สถานการณ์/เป้าหมาย

- **แรงผลัก:** เหตุผลที่ตัวละครลงมือ

- **อุปสรรค:** สิ่งที่ทำให้แผนยากขึ้น

- **จุดตัดสินใจ:** การเลือกที่เปลี่ยนเส้นทาง

- **ผลลัพธ์:** สำเร็จ ล้มเหลว หรือประนีประนอม

- **มรดก:** สิ่งที่เปลี่ยนต่อคน/ชุมชน/คนรุ่นถัดไป

หากข้อมูลไม่ครบ ให้เรียกว่า “บันทึกเหตุการณ์” ไม่ฝืนสร้างมหากาพย์เต็มรูปแบบ

## 10. การเก็บข้อมูล ประสิทธิภาพ และการบีบอัด

ระบบออนไลน์ต้องเก็บประวัติสำคัญยาวนาน แต่ไม่จำเป็นต้องเก็บทุก raw action ตลอดไป

### 10.1 นโยบายการเก็บรักษาเบื้องต้น

- Raw telemetry/action ย่อย: เก็บชั่วคราวตามความจำเป็นของการดีบัก เช่น 7–30 วัน

- Notable events: เก็บใน timeline ตามนโยบาย retention ของโลก และรวมได้เมื่อซ้ำ

- Chronicle events: เก็บถาวรแบบโครงสร้างกะทัดรัด

- Era-defining events: เก็บถาวร ห้ามยุบจนสูญ cause/effect หรือ facts สำคัญ

- Story summaries: เก็บเวอร์ชันพร้อม references ของ event ต้นทาง

### 10.2 การบีบอัดประวัติ

เมื่อ timeline ยาว:

1. เลือกกลุ่มเหตุการณ์ routine ที่มีชนิด/ตัวละคร/ช่วงเวลาใกล้กัน

2. สร้าง aggregate summary พร้อมตัวเลขรวมและ event references

3. เก็บ key events และ causal links แยกไว้

4. ทดสอบว่าเปิดสรุปแล้วยังสืบกลับไปยังข้อเท็จจริงได้

5. ห้ามลบข้อมูลที่เกี่ยวกับความตาย การเปลี่ยนสถานะถาวร มรดก หรือข้อพิพาทสำคัญโดยไม่มี archive reference

### 10.3 Event-driven processing

- สร้าง Chronicle เมื่อ event เกิด ไม่ poll ทุก NPC ทุกวินาที

- คำนวณ importance เฉพาะ event ที่ผ่านการตรวจ validity

- รวมเหตุการณ์ routine เป็น batch รายวัน/ฤดูกาล

- สร้าง/อัปเดต arc เฉพาะ arc ที่เชื่อมกับ event ใหม่

- สร้าง digest แบบ batch ตามรอบ ไม่สร้างใหม่ทุกครั้งที่เปิดหน้าจอ

- cache summary พร้อม version/hash เพื่อไม่ต้อง regenerate หากข้อมูลเดิม

### 10.4 ดัชนีค้นหา

Index ตาม entity_id, timestamp, region_id, event_type, arc_id และ visibility_scope แทนการค้นข้อความทั้ง archive ทุกครั้ง

## 11. การแก้ไข การอุทธรณ์ และความถูกต้อง

เหตุการณ์ใน Chronicle อาจต้องแก้เมื่อพบ bug หรือข้อมูลผิด แต่ไม่ควรเขียนประวัติใหม่เงียบ ๆ

- Canonical event มีสถานะ <u>valid</u>, <u>corrected</u>, <u>retracted</u>

- การแก้ไขสร้าง correction event ที่อ้างถึง event เดิม

- เก็บค่าเดิม/เหตุผล/เวลาแก้ใน audit log

- ข้อความ summary regenerate หลังแก้ canonical facts

- หากผู้เล่นส่งรายงาน ให้แนบ event_id ไม่ให้แก้ข้อความด้วย free text ในฐานข้อมูล

- การแก้ไขผลจากการโกงต้องบันทึก audit และไม่ทำให้ผู้เล่นทั่วไปคิดว่าโลกย้อนเวลาโดยไม่มีคำอธิบาย

## 12. ตัวอย่างสร้าง Chronicle จากเหตุการณ์จริง

ข้อมูล event

- ฤดูฝน วันที่ 14

- เรน่าและโทมะออกไปเก็บใบจันทร์ขาวตามคำขอของมีรา ผู้รักษาประจำหมู่บ้าน

- กลุ่มดาวส่งลางว่าทางเหนือมีฝูงมอนสเตอร์

- ปาร์ตี้อ้อมทางใต้ ใช้เสบียงเพิ่มหนึ่งหน่วย

- เก็บสมุนไพรได้ 12 หน่วยจากเป้าหมาย 10

- โทมะได้รับบาดเจ็บเล็กน้อยระหว่างทางกลับ

- มีราได้รับสมุนไพรและสต็อกยาหมู่บ้านเพิ่ม

- เหตุการณ์ลดระดับการขาดแคลนยา แต่ไม่ยุติความเสี่ยงเส้นทางเหนือ

หัวเรื่อง

**เรน่าพาปาร์ตี้กลับจากป่าพร้อมสมุนไพร แม้โทมะบาดเจ็บเล็กน้อย**

สรุปสั้น

ปาร์ตี้เลือกอ้อมเส้นทางเหนือหลังได้รับคำเตือนจากกลุ่มดาว และนำสมุนไพรกลับมาได้มากพอช่วยคลังยาของหมู่บ้าน

รายละเอียด

การอ้อมทำให้ใช้เสบียงเพิ่มและเดินทางนานขึ้น แต่ช่วยหลีกเลี่ยงฝูงมอนสเตอร์ที่มีรายงานทางเหนือ โทมะได้รับบาดเจ็บเล็กน้อยระหว่างเดินทางกลับ ขณะที่สมุนไพร 12 หน่วยช่วยลดภาวะขาดแคลนยาของหมู่บ้านจาก “วิกฤต” เป็น “ตึงตัว”

ผลต่อเนื่อง

- มีราอาจกลับมารับรักษาผู้ป่วยได้มากขึ้น

- เส้นทางเหนือยังเป็นความเสี่ยงสำหรับพ่อค้า

- ความไว้ใจ/ความสัมพันธ์ของปาร์ตี้เปลี่ยนตามการตัดสินใจและการแบ่งของ

ข้อความทุกส่วนอิง fact ที่บันทึกไว้ ไม่มีการสรุปว่ากลุ่มดาว “ช่วยชีวิต” หากไม่มีผลเชิงสาเหตุรองรับ

## 13. ตัวอย่าง Arc ของตัวละคร

Character Arc: จากผู้เก็บสมุนไพรสู่หัวหน้ากิลด์

1. **จุดเริ่ม:** เรน่าเป็นนักผจญภัยฝีมือกลาง มีเป้าหมายช่วยหมู่บ้าน

2. **เหตุการณ์ก่อตัว:** รับภารกิจเก็บสมุนไพรและช่วยผู้รักษา

3. **การทดสอบ:** ปาร์ตี้แตกแยกเรื่องความเสี่ยงและแบ่งรางวัล

4. **จุดตัดสินใจ:** เรน่าเลือกปันส่วนสมุนไพรให้ผู้ป่วยก่อนขาย

5. **ผลสะสม:** มีราและสมาชิกชุมชนเริ่มเคารพเธอ สมาชิกกิลด์บางคนเสนอให้เป็นหัวหน้าภารกิจ

6. **จุดเปลี่ยน:** กิลด์เผชิญข้อพิพาทเรื่องการใช้เงินสำรอง เรน่าต้องเลือกความโปร่งใสหรือรักษาผลประโยชน์กลุ่มตน

7. **สรุป Arc:** หากได้รับการยอมรับ เธออาจเป็นผู้นำ; หากล้มเหลว เธออาจออกจากกิลด์หรือกลับไปใช้ชีวิตนักผจญภัย

8. **Legacy:** หากเธอเป็นผู้ฝึกสอน ความรู้/แนวปฏิบัติอาจส่งต่อ แต่ลูกศิษย์ไม่สืบทอดบุคลิกหรือความสำเร็จของเธอโดยอัตโนมัติ

Arc สามารถจบได้หลายแบบและระบบไม่สร้างฉากบังคับเพื่อให้เธอกลายเป็นหัวหน้า

## 15. เกณฑ์ยอมรับระบบ Chronicle

1. เหตุการณ์สำคัญมีผู้เกี่ยวข้อง เวลา สถานที่ สาเหตุ และผลที่ตรวจสอบได้

2. ข้อความสรุปไม่เพิ่ม facts ที่ไม่มีใน event record

3. เหตุการณ์ routine ถูกยุบรวม แต่ยังค้นสถิติ/ยอดรวมได้

4. ผู้เล่นแยก canonical history, ข่าวลือ และความทรงจำของ NPC ได้

5. ผู้เล่นย้อนดูเรื่องราวของ NPC/องค์กร/ชุมชนโดยค้นหาได้

6. Chronicle เชื่อมเหตุการณ์ต้นเหตุและผลต่อเนื่องได้

7. สรุปมหากาพย์เลือกเหตุการณ์ที่มีความหมาย ไม่ใช่แค่เหตุการณ์ล่าสุดหรือ NPC ยอดนิยม

8. ความล้มเหลวและการถอยมีพื้นที่ในเรื่องราว ไม่ถูกซ่อนเหมือนเป็นผลที่ไม่ควรเกิด

9. การเปลี่ยนแปลง/แก้ไขประวัติมี audit/correction ไม่ rewrite เงียบ ๆ

10. การสร้าง summary ทำงานแบบ batch/event-driven และไม่ใช้ทรัพยากรเกินเหตุ

## 16. ลำดับการพัฒนา

1. สร้าง canonical event schema และ event lineage

2. เพิ่ม importance scoring, threshold และ dedup

3. ทำ timeline ตาม NPC/ชุมชน พร้อมข้อความจาก template

4. เพิ่ม cause/effect links และ event inspector ภายใน

5. เพิ่ม Arc Builder สำหรับ character/party/community อย่างละหนึ่งแบบ

6. เพิ่ม summaries รายวัน/ฤดูกาล/บท

7. เพิ่ม family/guild/faction/world history และการค้นหา

8. พิจารณา LLM ช่วยปรับสำนวนเฉพาะเมื่อระบบ facts, visibility และ validation เสถียร

## 17. สรุปหลักการ

Dynamic Chronicle ที่ดีไม่ใช่การสร้างข้อความให้ยาวที่สุด แต่คือการเลือก **เหตุการณ์ที่เปลี่ยนชีวิต** แล้วเล่าด้วยสาเหตุและผลที่เป็นจริง

ระบบควร:

- บันทึก facts ก่อนเขียนคำบรรยาย

- คัดแยก routine ออกจาก turning point

- เชื่อมเหตุการณ์เป็น arc ที่เกิดจากระบบ ไม่ใช่บังคับพล็อต

- รักษาสิทธิ์การมองเห็นและความรู้ของ NPC/ผู้เล่น

- เก็บเหตุการณ์สำคัญยาวนาน พร้อมบีบอัดรายละเอียดเล็กอย่างตรวจสอบย้อนกลับได้

- สรุปได้ทั้งชีวิตบุคคล ชุมชน องค์กร และยุคสมัย

**คำถามพิสูจน์ระบบ:** ผู้เล่นย้อนดูแล้วตอบได้หรือไม่ว่า “เกิดอะไรขึ้น ทำไมจึงเกิด และมันเปลี่ยนใคร/โลกอย่างไร” โดยไม่ต้องพึ่งความจำจากการเล่นสด?
