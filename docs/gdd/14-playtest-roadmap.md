# แผนกลยุทธ์ Playtest Roadmap

> **สถานะ (docs/DECISIONS.md):** ⚠️ ใช้ P0–P2 แบบเล่นคนเดียว — P3 ขึ้นไปสำหรับระยะออนไลน์  
> ถ้าเนื้อหาในไฟล์นี้ขัดกับ [DECISIONS.md](../DECISIONS.md) ให้ยึด DECISIONS.md · ตัวเลขดู [BALANCE.md](../BALANCE.md)

การทดสอบระบบโซเชียลและอารยธรรม NPC แบบเป็นขั้น

**เกม:** พงศาวดารใต้ดวงดาว  
**เป้าหมาย:** พิสูจน์ว่า NPC สามารถสร้างชีวิต ความสัมพันธ์ เศรษฐกิจ องค์กร และประวัติศาสตร์ได้อย่างน่าเชื่อถือในโลกออนไลน์ร่วมกัน โดยกลุ่มดาวมีผลต่อโลกแต่ไม่ครอบงำหรือทำลายโลก  
**เวอร์ชัน:** 0.1 — แผนตั้งต้นสำหรับทีมขนาดเล็ก/ต้นแบบออนไลน์

**กลยุทธ์หลัก:** อย่าเปิดระบบทั้งหมดให้ผู้เล่นพร้อมกันตั้งแต่วันแรก ให้ทดสอบจาก “ความจริงของ simulation” → “เรื่องราวของ NPC” → “สังคมและองค์กร” → “อิทธิพลกลุ่มดาว” → “วิกฤต/Co-op” → “ประวัติศาสตร์และเสียง” แล้วค่อยทำ closed beta แบบต่อเนื่อง

## 1. สมมติฐานและขอบเขตแผน

แผนนี้สมมติว่าเกมเป็นโลกออนไลน์ร่วมกันแบบ asynchronous ผู้เล่นเป็นกลุ่มดาว และ NPC/องค์กรเป็นผู้ดำเนินชีวิตหลัก เป้าหมายคือทดสอบระบบที่ออกแบบในภาคผนวกก่อนหน้า ได้แก่:

- NPC Simulation / Behavior Tree และเศรษฐกิจ NPC-driven

- ความสัมพันธ์ ครัวเรือน Generation & Legacy

- กิลด์ Factions ชุมชน และการเติบโตเป็นอาณาจักร

- อิทธิพล คูลดาวน์ การร่วมมือ/แข่งขันระหว่างกลุ่มดาว

- Global Events และ Constellation Raid / Co-op Quests

- Game Balance & Anti-Griefing

- Dynamic Chronicle & History Generation

- Dynamic Audio ตามยุคและความเจริญ

ขนาดผู้เล่นและจำนวน NPC ในแต่ละช่วงด้านล่างเป็น **ค่าเริ่มต้นสำหรับการวางแผน** ต้องปรับตาม capacity ที่วัดได้จาก profiling ไม่ใช่การรับประกันความจุเซิร์ฟเวอร์

หลักการด้านข้อมูลทดสอบ

- ใช้ test shard แยกจาก production และแยกบัญชี/ความก้าวหน้าชัดเจน

- แจ้งผู้เข้าร่วมก่อนเริ่ม หากโลกจะ reset, เปลี่ยนกฎ หรือมีข้อมูลถูกล้าง

- ไม่โอนรางวัล/ทรัพย์สินจาก test ไปโลกจริง เว้นแต่มีประกาศกติกาชัด

- เก็บ telemetry เท่าที่จำเป็น มี event ID และ anonymize ข้อมูลวิเคราะห์

- ห้ามใช้ข้อมูลผู้เล่นทดสอบเป็นหลักฐานลงโทษจากการเลือกผลลัพธ์ในเกมที่กติกาอนุญาต

## 3. กติกาการออกแบบ Playtest

### 3.1 หนึ่งระยะมีคำถามหลักไม่กี่ข้อ

ในแต่ละระยะกำหนดคำถามสำคัญ 2–4 ข้อ เช่น “NPC อยู่รอดโดยไม่มีผู้เล่นได้หรือไม่?” หรือ “ผู้เล่นเข้าใจเหตุผลที่ NPC ปฏิเสธคำชี้นำหรือไม่?” หลีกเลี่ยงการเปลี่ยนตัวเลข ระบบ UI และเนื้อหาหลายชิ้นพร้อมกันจนระบุสาเหตุไม่ได้

### 3.2 แยก test สองชนิด

- **Simulation test:** ใช้ seed/agent จำนวนมาก ตรวจเสถียรภาพ ความถูกต้อง และภาวะสุดขั้ว

- **Human playtest:** ตรวจความเข้าใจ ความรู้สึก ความยุติธรรม ความสนุก และการอ่านเหตุผลของโลก

ให้ใช้ simulation test หา bug ก่อน แล้วใช้ผู้เล่นประเมินคุณภาพการออกแบบ ไม่ใช้ผู้เล่นเป็นเครื่องมือหาบั๊กพื้นฐานที่ระบบอัตโนมัติจับได้

### 3.3 หลีกเลี่ยงการทดสอบแบบกล่องดำ

เหตุการณ์สำคัญทุกชิ้นมีเหตุผลใน debug/event log แม้ไม่เปิดข้อมูลทั้งหมดแก่ผู้เล่น ทีมต้องตรวจย้อนหลังได้ว่า NPC เลือก action จากอะไรและแต้ม/ทรัพยากรเปลี่ยนอย่างไร

### 3.4 ใช้ feature flags และ release gates

เปิด/ปิดเฉพาะระบบหรือความสามารถได้ เช่น:

- ปิดการสร้างอาณาจักรแต่คงกิลด์

- ปิดพลังกลุ่มดาวระดับสูง

- ใช้ Global Event แบบจำลองโดยไม่ commit ผลถาวร

- ปิดรางวัลระหว่าง balance test

- ลดจำนวน NPC หรือความถี่จำลองโดยไม่เปลี่ยนกฎหลัก

## 4. ระยะ P0 — Simulation Lab / โลกจำลองอัตโนมัติ

**ระยะเวลาแนะนำ:** 2–3 สัปดาห์ และรันซ้ำตลอดการพัฒนา  
**ผู้ทดสอบ:** ทีมระบบ/QA; ไม่มีผู้เล่นภายนอก  
**คำถามหลัก:** โลก NPC และเศรษฐกิจทำงานได้โดยไม่ต้องมีผู้เล่นช่วยประคองหรือไม่?

ขอบเขต

- Behavior Tree/Utility AI และกิจวัตร

- การผลิต การค้า การบริโภค สต็อก และราคา

- ความสัมพันธ์และ event ที่เปลี่ยนความสัมพันธ์

- ประชากร/ครัวเรือนแบบ cohort และการเติบโตตามรุ่น

- กิลด์/Faction ขั้นต้น

- Event Director และ recovery path แบบจำลอง

รูปแบบทดสอบ

- หลาย world seed และความเร็วเวลาหลายระดับ

- โลกสมบูรณ์ / ขาดแคลน / เส้นทางขาด / ผู้นำหาย / ภัยซ้อน

- ปิด player intervention ทั้งหมด แล้วดูว่า NPC ดำเนินต่ออย่างไร

- เปิดการแทรกแซงสุดขอบเพื่อพิสูจน์ว่าเพดาน/validation ทำงาน

- ใช้ stress load แยกจาก human test โดยเพิ่ม agent/เหตุการณ์ตาม capacity

ตัวชี้วัดและ Gate

- ธุรกรรมสำคัญมีบัญชีต้นทาง–ปลายทางครบ ไม่มีเงิน/สินค้าซ้ำจากการ resolve event ซ้ำ

- ไม่มีการขาดบริการพื้นฐานถาวรโดยไม่มีสาเหตุหรือ recovery path

- เหตุการณ์ซ้ำ/สภาวะเปราะบางนำไปสู่ผลที่คาดการณ์และตรวจสอบได้

- simulation queue ไม่สะสมเกินกรอบที่ทีมกำหนด; ตั้งเป้าความล่าช้า p95 ต่ำกว่าหนึ่งรอบการจำลองที่สำคัญ

- NPC ไม่ติดพฤติกรรมเดียวไม่สิ้นสุดจาก action loop ที่ไม่มีความคืบหน้า

- ทุกผลลัพธ์สำคัญอ้างอิง event ID และสามารถ replay ใน test ได้

ไม่ผ่านเมื่อ

เกิดเศรษฐกิจเฟ้อ/พังโดยไร้ตัวแปรอธิบาย, NPC สร้างของไม่จำกัด, event เดิม resolve ซ้ำ หรือโลกไม่สามารถฟื้นจากสถานการณ์ทดสอบได้

## 5. ระยะ P1 — Internal Playtest / ตรวจแกนเกมและเครื่องมือทีม

**ระยะเวลาแนะนำ:** 1–2 สัปดาห์  
**ผู้ทดสอบ:** ทีม 5–10 คน เล่นบทบาทต่างกัน  
**คำถามหลัก:** ทีมเข้าใจสถานะโลกและสาเหตุของการตัดสินใจ NPC ได้หรือไม่?

ขอบเขต

- UI มุมมองกลุ่มดาวและหน้าต่าง NPC

- ดูความสัมพันธ์/กิจวัตร/เศรษฐกิจ

- ส่งลางหรือพรพื้นฐานใน event ขนาดเล็ก

- Chronicle แบบ template เบื้องต้น

- ใช้เครื่องมือ debug: event inspector, economy ledger, NPC decision trace

กรณีทดสอบ

- ติดตาม NPC หนึ่งคนตลอดหลายวันเกม

- สังเกตปาร์ตี้/ครอบครัว/กิลด์หนึ่งชุด

- ส่งการชี้นำที่ NPC ทำตามและปฏิเสธ

- ทดสอบผู้เล่นออฟไลน์/กลับมาแล้วอ่านสรุปย้อนหลัง

- ทำการส่งคำสั่งซ้ำ/หลุดระหว่างส่ง/กดปุ่มซ้ำ

Gate

- ผู้ทดสอบทีมตอบได้ว่า NPC เลือก action เพราะอะไรจากข้อมูลที่ UI เปิดให้

- ทุก action ที่ปฏิเสธมีเหตุผลที่เข้าใจได้ เช่น ขาดทรัพยากร/ไม่เชื่อข้อมูล/มีเป้าหมายขัดกัน

- event log แสดงความแตกต่างระหว่าง canonical fact กับข้อความสรุป

- ไม่มี P0/P1 defect ในธุรกรรมหรือการ commit อิทธิพลก่อนรับผู้เล่นนอกทีม

## 6. ระยะ P2 — Friends & Family / Usability Test

**ระยะเวลาแนะนำ:** 2 สัปดาห์  
**ผู้ทดสอบ:** 20–40 คนที่ไม่ใช่ทีมพัฒนา; เน้นผู้เล่นใหม่และผู้เล่นที่ชอบสังเกต  
**คำถามหลัก:** ผู้เล่นเข้าใจบทบาท “กลุ่มดาว” และรู้สึกว่าการเฝ้ามอง NPC น่าสนใจหรือไม่?

เปิดระบบ

- โลกขนาดเล็กหนึ่งภูมิภาค

- NPC มีชีวิตประจำวันและเศรษฐกิจพื้นฐาน

- ความสัมพันธ์พื้นฐาน/ปาร์ตี้/กิจการไม่กี่ประเภท

- การดู NPC, Watchlist, Chronicle timeline ขั้นต้น

- การชี้นำพลังระดับ 0–2 เท่านั้น

ยังไม่เปิด

- พลังเชิงลบหรือการเปลี่ยนอารยธรรม

- สงครามระหว่าง Factions

- อาณาจักรเต็มระบบ

- open chat และระบบรางวัล/เศรษฐกิจที่ให้ประโยชน์จริงนอก test

วิธีทดสอบ

- ทดสอบแบบมีโจทย์ เช่น “ติดตาม NPC คนหนึ่งและบอกว่าเป้าหมายวันนี้คืออะไร”

- ให้เล่นอิสระโดยไม่สอนทุกเมนู

- สัมภาษณ์หลังเล่นเรื่องความผูกพัน/ความเข้าใจ/สิ่งที่สับสน

- เก็บ telemetry การเปิด panel, อ่าน event, ส่ง intervention และออกจากระบบ โดยไม่เน้นเวลาหน้าจออย่างเดียว

Gate

- ผู้ทดสอบส่วนใหญ่เข้าใจว่า NPC ไม่ใช่ตัวละครที่ตนควบคุม

- ผู้เล่นหาเป้าหมาย/สถานะ NPC ได้โดยไม่ต้องพึ่งทีมช่วยตลอด

- ผู้เล่นเห็นผลการชี้นำอย่างน้อยหนึ่งแบบและเข้าใจว่าเหตุใดผลไม่รับประกัน

- ไม่มีปัญหาความเป็นส่วนตัว/ข้อความ/การแจ้งเตือนที่ทำให้ผู้เล่นไม่สบายใจ

## 7. ระยะ P3 — Closed Social Alpha / ความสัมพันธ์และองค์กร

**ระยะเวลาแนะนำ:** 3–4 สัปดาห์  
**ผู้ทดสอบ:** 50–100 คนแบบเชิญ; ผู้เล่นเดี่ยวและกลุ่มเล็กคละกัน  
**คำถามหลัก:** ความสัมพันธ์และองค์กรเกิดจากพฤติกรรมของ NPC อย่างมีเหตุผล และผู้เล่นหลายคนอยู่ร่วมกันได้หรือไม่?

เปิดระบบ

- Social Network หลายมิติ

- ครัวเรือน/คู่ชีวิต/การถ่ายทอดทักษะและ Legacy ในระดับจำกัด

- กิลด์ 1–2 ประเภท มีสมาชิก งบ และการรับงานจริง

- Faction/กลุ่มผลประโยชน์ระดับชุมชน

- การร่วมมือหรือเห็นต่างระหว่างกลุ่มดาวแบบไม่มีการทำลายโดยตรง

- Chronicle ของตัวละคร/องค์กร

Test scenarios

- สมาชิกกิลด์มีความเห็นขัดกันเรื่องใช้เงิน/เลือกผู้นำ

- NPC ผู้ใหญ่สองคนเริ่ม/ไม่เริ่มความสัมพันธ์จากปัจจัยต่างกัน

- NPC ออกจากองค์กรเพราะค่าตอบแทนหรือความไว้วางใจลด

- ทายาท/ลูกศิษย์รับช่วงกิจการแต่ไม่สืบทอดความสามารถทั้งหมด

- ผู้เล่นเดี่ยวเทียบกับสมาชิกวงดาว: ตรวจว่าผู้เล่นเดี่ยวไม่ถูกกันออกจากระบบ

Gate

- ความสัมพันธ์เปลี่ยนจาก event จริงและมีทิศทาง ไม่ถูกยุบเป็นค่าเดียว

- กิลด์มีรายรับรายจ่ายและแรงจูงใจของสมาชิกที่ตรวจสอบได้

- ไม่มีการบังคับความสัมพันธ์/การแต่งงานจากผู้เล่น

- ผู้เล่นกลุ่มใหญ่ไม่สามารถล็อก NPC หรือผูกขาด event

- การออกจากวง/กิลด์ไม่ลบความก้าวหน้าหรือประวัติส่วนตัว

## 8. ระยะ P4 — Crisis & Co-op Integration Test

**ระยะเวลาแนะนำ:** 3–4 สัปดาห์  
**ผู้ทดสอบ:** 100–250 คนแบบ wave; load test สังเคราะห์แยกจากกลุ่มคนจริง  
**คำถามหลัก:** Global Events และ Co-op quests ทดสอบระบบสังคม/เศรษฐกิจได้จริงโดยไม่บังคับออนไลน์พร้อมกันหรือไม่?

เปิดระบบ

- Global Events 2–3 archetypes ที่ผ่าน Simulation Lab

- Event Director จำกัดวิกฤตซ้อนและแสดง telegraph

- กลุ่มดาวช่วยหลายหมวดโดยใช้แต้มส่วนตัวและ global cap

- Co-op Quest / Raid แบบ asynchronous; เริ่มจาก 1–3 เฟสก่อนขยาย

- NPC/กิลด์/ชุมชนตอบสนองอัตโนมัติแม้ไม่มีผู้เล่น

- recovery path และ Chronicle สรุปผล

กรณีทดสอบ

- ผู้เล่นไม่ช่วย / มีผู้เล่นช่วยน้อย / มีผู้เล่นจำนวนมากช่วยหมวดเดียว / สนับสนุนคนละทิศ

- ผู้เล่นเข้ามาหลัง phase แรกและหลัง event จบ

- ผู้เล่นต่างเขตเวลาเข้าร่วมคนละช่วง

- ผลลัพธ์ดีบางส่วน/ล้มเหลว/ถอนตัวอย่างมีแผน

- ทดลองบัญชีหลายบัญชีใน test เพื่อยืนยัน global cap โดยไม่เปิดเผยข้อมูลจริง

Gate

- ไม่มีภัยใหญ่เกิดแบบไร้สัญญาณเตือนหรือไม่มีทางแก้

- จำนวนผู้เล่นไม่ทำให้ภัยสเกลยากขึ้นโดยอัตโนมัติ

- เมื่อไม่มีผู้เล่น NPC ยังแก้/ประคองวิกฤตได้ตามทรัพยากรจริง

- กลุ่มดาวมีผลที่เห็นได้แต่ไม่รับประกันชัยชนะ

- อิทธิพล/สินค้า/รางวัลไม่ถูกสร้างซ้ำจาก disconnect หรือ resolve ซ้ำ

- ผลล้มเหลวเปิด recovery quests แทนการทำให้ชุมชน dead-end

## 9. ระยะ P5 — Closed Beta Season / อารยธรรมหลายภูมิภาค

**ระยะเวลาแนะนำ:** 4–6 สัปดาห์ต่อ season ทดสอบ  
**ผู้ทดสอบ:** 200–500 คนเป็นรอบตาม capacity ที่วัดได้; เปิดเพิ่มเป็น wave ไม่เปิดทั้งหมดทีเดียว  
**คำถามหลัก:** ระบบหลายสเกลยังรักษาความต่อเนื่องของโลกและความยุติธรรมเมื่อทดสอบต่อเนื่องหรือไม่?

เปิดระบบเพิ่ม

- 2–3 ภูมิภาคที่มีสถานะเศรษฐกิจ/วัฒนธรรมต่างกัน

- การเติบโตจากชุมชนสู่เมือง/สมาพันธ์แบบจำกัด

- การเปลี่ยนผู้นำ/ความชอบธรรม/ความขัดแย้งภายใน

- Generation & Legacy ต่อเนื่องอย่างน้อย 1 ช่วงรุ่นแบบเร่งเวลา test

- Chronicle ระดับโลก/ฤดูกาลและ Dynamic Audio 2–3 สถานะ

- ปฏิสัมพันธ์กลุ่มดาวร่วมมือ/แข่งขันเชิงเรื่องราว

รูปแบบ Season

1.  **สัปดาห์เตรียม:** โลกตั้งต้นและผู้เล่นเรียนรู้ระบบ

2.  **สัปดาห์แรงกดดัน:** เปิด event ที่มี telegraph

3.  **สัปดาห์ผลต่อเนื่อง:** เศรษฐกิจ/องค์กรตอบสนอง

4.  **สัปดาห์ฟื้นฟู/ทบทวน:** Chronicle สรุปและเก็บ feedback

หลีกเลี่ยงการออกแบบ season ที่ต้องล็อกอินทุกวันเพื่อไม่ให้สูญเสียความก้าวหน้า

Gate

- รัฐ/สมาพันธ์เกิดจากประชากร ทรัพยากร การบริหารและความชอบธรรม ไม่ใช่สุ่มชื่อหรือผู้เล่นปั๊มแต้ม

- การเปลี่ยนรุ่นทำให้โลกเปลี่ยนแต่ยังมีเส้นทางเล่นต่อ

- ผู้เล่นกลับหลังหายไปหลายวันยังเข้าใจว่าโลกเปลี่ยนอะไรจาก Chronicle/สรุป

- Dynamic Audio เปลี่ยนตามสถานะโลกอย่างนุ่มนวลและไม่ทำให้ข้อมูลเกมหาย

- ไม่มี P0/P1 issue ด้าน persistence, economy, privacy หรือ exploit ค้างก่อนเริ่มรอบใหม่

## 10. ระยะ P6 — Staged Public Test (เมื่อผ่าน Gate)

**ระยะเวลา:** เปิดเป็น wave; ประเมินทุก 48–72 ชั่วโมงช่วงแรก  
**จำนวนผู้เล่น:** เริ่มจาก 100–300 คน แล้วขยายเป็น 500+ หรือระดับที่ infrastructure/load test รองรับจริง  
**คำถามหลัก:** ระบบยังคงน่าเชื่อถือและอ่านเข้าใจได้เมื่อมีผู้เล่นที่ไม่รู้จักกันจำนวนมากหรือไม่?

วิธีขยาย

- เปิด waitlist/รอบเวลา ไม่เปิดทุกภูมิภาคพร้อมกัน

- เริ่มด้วย feature set ที่ผ่าน Closed Beta เท่านั้น

- ขยายจำนวนผู้เล่นทีละระดับเมื่อ queue lag, error rate และ economy pass thresholds

- คง staging shard สำหรับทดสอบ patch ก่อนลง public world

- เตรียม status page/ประกาศปัญหาและวิธีคืนค่าที่โปร่งใส

เกณฑ์หยุดการขยาย

หยุดรับ wave ใหม่หรือปิด feature flag เฉพาะระบบเมื่อ:

- ธุรกรรมเศรษฐกิจซ้ำ/หาย หรือ Chronicle facts ไม่ตรงสถานะจริง

- คิวจำลองสะสมเกินช่วงเวลาที่กำหนดต่อเนื่อง

- พบช่องโหว่ที่ทะลุ global cap หรือสร้างทรัพยากรไม่จำกัด

- ระบบมอบหมายเหตุการณ์ทำให้ชุมชนล้มถาวรโดยไม่มีเหตุ/ทางฟื้น

- มีปัญหาความเป็นส่วนตัวหรือการก่อกวนที่ผู้เล่นป้องกันตัวเองไม่ได้

การหยุดต้องจำกัดเท่าที่จำเป็น ไม่ reset โลกโดยอัตโนมัติ และแจ้งผู้เล่นว่าเกิดอะไร/ผลต่อข้อมูลอย่างไร

## 12. ตัวชี้วัดหลัก (North-star + Guardrails)

### 12.1 คุณภาพเรื่องราวและความเข้าใจ

- **เหตุผลที่เข้าใจได้:** ผู้เล่นอธิบายสาเหตุของการเปลี่ยนแปลง NPC/ชุมชนได้

- **เรื่องราวที่ผู้เล่นจำได้:** หลัง session ผู้เล่นเล่าเหตุการณ์ NPC ที่น่าสนใจได้ โดยไม่ต้องชี้นำคำตอบ

- **ความต่อเนื่อง:** ผู้เล่นที่กลับหลังออฟไลน์เข้าใจว่าเกิดอะไรขึ้นจาก recap

- **ความรู้สึกมีอิทธิพล:** ผู้เล่นเห็นผลจาก action แต่ยอมรับได้เมื่อ NPC ตัดสินใจต่าง

### 12.2 ความเสถียรของ simulation

- อัตราธุรกรรมที่มี ledger ครบ

- จำนวน event ที่ resolve ซ้ำ/ไม่ idempotent

- ความล่าช้าของ simulation queue เทียบกับรอบโลก

- สัดส่วน NPC ที่ติด action loop หรือไม่มีเป้าหมายต่อเนื่อง

- ความถี่ที่บริการพื้นฐานต่ำกว่าจุดสำรองและมี/ไม่มี recovery path

### 12.3 ความยุติธรรมและ anti-griefing

- ผลรวมผู้เล่นต่อเป้าหมายถูกจำกัดด้วย global cap

- ความต่างของโอกาส/ผลระหว่างผู้เล่นเดี่ยวและวงใหญ่

- จำนวน action ถูกปฏิเสธจากเหตุผลที่ UI อธิบายได้

- จำนวน exploit/คำสั่งซ้ำและเวลาตรวจแก้

- จำนวน report ที่ยืนยัน/ไม่ยืนยัน ไม่ใช้เป็นตัวลงโทษอัตโนมัติ

### 12.4 Social Health

- อัตราก่อตั้ง/เสื่อม/แตกกิลด์และเหตุผล

- การคงอยู่ของความสัมพันธ์ที่มี event รองรับ

- ความหลากหลายของรูปแบบครัวเรือนและเส้นทางสืบทอด

- อัตราความขัดแย้งที่คลี่คลาย/ยืดเยื้อ/ลุกลาม

- การกระจายความช่วยเหลือระหว่างชุมชนและผลต่อความชอบธรรม

### 12.5 Audio/UX

- อัตราการเปลี่ยน layer ที่ถี่หรือสั่นจาก hysteresis ไม่พอ

- สัดส่วนผู้เล่นลด/ปิดเสียง adaptive และเหตุผล

- จำนวน cue ซ้ำ/ผิดเวลา/เล่นหลัง reconnect

- active voices, memory, CPU และ streaming stalls

**หลักใช้ metric:** ใช้หาคำถามและแนวโน้ม ไม่ตีความตัวเลขเดี่ยวเป็นคุณภาพเกมทั้งหมด

## 13. วิธีเก็บ Feedback

ใช้ช่องทางหลายแบบเพื่อไม่ให้ feedback มาจากผู้เล่นสายหนึ่งเท่านั้น:

1.  แบบสอบถามสั้นหลังจบ session โดยถามเรื่องเหตุการณ์เฉพาะ

2.  สัมภาษณ์ผู้เล่นที่มีรูปแบบต่างกัน: ผู้สังเกต ผู้ชี้นำ ผู้เข้าวง และผู้เล่นเดี่ยว

3.  session observation ที่ขอความยินยอมและไม่เก็บข้อมูลเกินจำเป็น

4.  feedback พร้อม event ID/ตำแหน่งหน้าจอ เพื่อเชื่อมกับ log ได้

5.  player diary ระยะสั้นช่วง Closed Beta: “วันนี้โลกเปลี่ยนอะไรที่คุณจำได้?”

6. สรุปสิ่งที่ทีมแก้/ยังไม่แก้ พร้อมเหตุผลให้ผู้ทดสอบเห็น

คำถามกลาง

- NPC คนใดที่คุณสนใจ และเพราะอะไร?

- คุณเชื่อไหมว่าเหตุการณ์นี้เกิดจากระบบโลก ไม่ใช่สุ่มเพื่อบังคับเล่น?

- ตอนไหนที่คุณไม่เข้าใจว่าทำไม NPC เลือกเช่นนั้น?

- การชี้นำของคุณมีความหมายหรือรู้สึกไร้ผล/แรงเกินไป?

- หากคุณกลับมาอีกหนึ่งสัปดาห์ คุณอยากรู้เรื่องอะไรของโลกก่อน?

## 15. การปล่อย patch และการ rollback

ก่อนแต่ละรอบ:

1. บันทึก world snapshot และ schema/rules version

2. ทดสอบ migration บนสำเนา

3. รัน seeded simulations กับกฎใหม่

4. เปรียบเทียบผลลัพธ์ก่อน/หลังแบบ distribution ไม่ใช่ตัวอย่างเดียว

5. เปิด feature flag ให้กลุ่มเล็กก่อน

6. ตรวจ error, ledger, queue lag, social/economic guardrails

7. ขยายหรือ rollback เฉพาะระบบที่มีปัญหา

หากต้องปรับระบบกลางโลก ให้แสดง patch note ที่อธิบายผลต่อ NPC/เศรษฐกิจ/Chronicle และอย่าแก้ประวัติเดิมโดยไม่บันทึก correction event

## 17. สรุปกลยุทธ์

การทดสอบระบบอารยธรรม NPC ควรเริ่มจากการถามว่า **โลกทำงานถูกต้องและอยู่ต่อได้หรือไม่** ก่อนถามว่า **ผู้เล่นสนุกกับโลกนั้นหรือไม่** จากนั้นจึงเพิ่มความสัมพันธ์ องค์กร วิกฤต และการแสดงผลทางประวัติศาสตร์ทีละชั้น

ลำดับที่แนะนำ:

1. พิสูจน์ AI/เศรษฐกิจด้วย simulation seeds

2. ให้ทีมภายในตรวจเหตุผลและเครื่องมือ debug

3. ทดสอบความเข้าใจบทบาทกลุ่มดาวกับผู้เล่นกลุ่มเล็ก
