**วัตถุประสงค์:** ออกแบบระบบที่ขับเคลื่อนชีวิตประจำวัน การทำงาน การซื้อขาย การเข้าสังคม การรวมปาร์ตี้ และการผจญภัยของ NPC โดยไม่ต้องใช้ AI สร้างข้อความหรือคิดใหม่ทุกเฟรม  
**แนวทางหลัก:** ใช้สถาปัตยกรรมผสม **Utility AI + Behavior Tree + Event-driven Simulation**  
**เวอร์ชัน:** 0.1 — ข้อเสนอตั้งต้นสำหรับต้นแบบ  
**ข้อกำหนดทรัพยากร:** ให้คำนวณตามเหตุการณ์และรอบเวลา ใช้การจำลองละเอียดเฉพาะ NPC/พื้นที่ที่เกี่ยวข้อง และไม่เรียกโมเดลภาษาสำหรับการตัดสินใจปกติ

**แนวคิดสั้น:** Utility AI ตัดสินว่า “ตอนนี้อะไรสำคัญที่สุด” ส่วน Behavior Tree จัดลำดับว่า “จะลงมือทำอย่างไร” และระบบเหตุการณ์เป็นผู้แจ้งว่า “มีอะไรเปลี่ยนจนต้องคิดใหม่”

## 1. เป้าหมายของระบบ NPC

NPC ต้องทำให้ผู้เล่นรู้สึกว่าพวกเขาเป็นคนในโลก ไม่ใช่เอเจนต์สุ่มเดินไปมา ระบบจึงต้องทำให้พฤติกรรมมีคุณสมบัติต่อไปนี้:

1.  **มีแรงจูงใจ:** NPC ทำสิ่งต่าง ๆ เพื่อสนองความต้องการ เป้าหมาย หรือหน้าที่

2.  **มีข้อจำกัด:** เงิน เวลา สุขภาพ ทักษะ ข่าวสาร ความสัมพันธ์ และการเดินทางมีผลจริง

3.  **ต่อเนื่อง:** NPC จดจำเหตุการณ์ที่มีความหมายและเปลี่ยนพฤติกรรมในอนาคต

4.  **เข้าใจได้:** ผู้เล่นเห็นเหตุผลหลักของการเลือก ไม่รู้สึกว่าระบบสุ่มโดยไร้ที่มา

5.  **แตกต่างกัน:** บุคลิก ทักษะ และสถานการณ์ทำให้ NPC ตอบสนองไม่เหมือนกัน

6.  **ประหยัดทรัพยากร:** ไม่จำลอง NPC ทุกคนทุกวินาที และไม่คำนวณซ้ำเมื่อไม่มีข้อมูลเปลี่ยน

7.  **ทดสอบซ้ำได้:** ใช้ seed และกฎที่กำหนดได้ เพื่อทำซ้ำเหตุการณ์และแก้บั๊ก

8.  **ไม่แย่งบทผู้เล่น:** กลุ่มดาวชี้นำได้ แต่ NPC ยังคงมีสิทธิ์เลือก ปฏิเสธ หรือเปลี่ยนใจ

สิ่งที่ไม่ต้องการ

- NPC ตัดสินใจด้วย LLM ทุกครั้งที่ต้องกินหรือเดินทาง

- บุคลิกเป็นข้อความตกแต่งที่ไม่เปลี่ยนพฤติกรรม

- NPC รู้ข้อมูลที่ไม่เคยเห็น/ได้ยิน

- NPC ทำภารกิจเดิมซ้ำโดยไม่ตรวจสต็อกหรือความต้องการ

- ใช้ randomness แทนเหตุและผล

- Behavior Tree ขนาดใหญ่อันเดียวที่ยากต่อการดูแลและปรับแก้

## 2. สถาปัตยกรรม AI ที่แนะนำ

ใช้ระบบห้าชั้นแยกหน้าที่ชัดเจน

ชั้นที่ 1: World / Event State

เก็บข้อเท็จจริงของโลก เช่น เวลา สภาพอากาศ สต็อกสินค้า ราคาล่าสุด ภัยตามพื้นที่ ภารกิจ และสถานะตัวละคร ระบบอื่นอ่านข้อมูลชั้นนี้ แต่ไม่แก้โดยตรงโดยไม่มีคำสั่ง/ธุรกรรมที่ตรวจสอบได้

ชั้นที่ 2: Perception และความรู้ของ NPC

กรองข้อมูลโลกให้เป็นสิ่งที่ NPC **รู้หรือเชื่อ** เช่น มองเห็นอันตราย ได้ยินข่าวลือ ได้รับคำสั่งจากนายจ้าง หรือจำเหตุการณ์ก่อนหน้า NPC ไม่ได้อ่าน world state ทั้งหมดโดยอัตโนมัติ

ชั้นที่ 3: Goal Selection — Utility AI

เลือกความต้องการหรือเป้าหมายที่ควรทำก่อน เช่น หาอาหาร รักษาตัว ทำงาน ซื้อวัตถุดิบ ช่วยเพื่อน หรือรับภารกิจ โดยประเมินประโยชน์ ความเร่งด่วน ความเป็นไปได้ ความเสี่ยง และค่าใช้จ่าย

ชั้นที่ 4: Goal Execution — Behavior Tree

เมื่อเลือกเป้าหมายแล้ว Behavior Tree (BT) ทำงานเป็นขั้น เช่น ตรวจเงื่อนไข → เตรียมเงิน/อุปกรณ์ → เดินทาง → ซื้อของ → กลับไปทำกิจกรรม หากเหตุการณ์ใหม่ทำให้แผนใช้ไม่ได้ BT หยุดหรือสลับเป้าหมายตามกฎ

ชั้นที่ 5: Action / Transaction Resolver

การกระทำที่เปลี่ยนโลกจริง เช่น ซื้อของ จ่ายเงิน ผลิตสินค้า รับภารกิจ หรือใช้ทรัพยากร ต้องผ่าน action resolver ที่ตรวจเงื่อนไขและบันทึกธุรกรรม ไม่แก้ตัวเลขโดยตรงจาก tree node

> World Events
>
> ↓
>
> Perception / NPC Knowledge
>
> ↓
>
> Needs + Goals + Utility Scoring
>
> ↓
>
> Behavior Tree executes selected goal
>
> ↓
>
> Validated Action / Economy Transaction
>
> ↓
>
> World State + Chronicle Event

**ข้อเสนอสำหรับ MVP:** ไม่ต้องเพิ่ม GOAP เต็มรูปแบบในตอนแรก เพราะ Utility AI + BT พร้อม action set ขนาดเล็กให้ความยืดหยุ่นพอและง่ายต่อการอธิบาย/ทดสอบ

## 3. หน่วยจำลองและระดับความละเอียด

### 3.1 NPC สำคัญ (Hero/Named NPC)

จำลองรายบุคคล มีความต้องการ ความสัมพันธ์ ความทรงจำ เป้าหมาย และการตัดสินใจในระดับกิจกรรม สามารถเป็นตัวละครที่ผู้เล่นจับตามองได้

### 3.2 NPC ท้องถิ่น (Local Agent)

จำลองรายบุคคลเฉพาะข้อมูลที่จำเป็นต่ออาชีพ/บริการ เช่น พ่อค้า ผู้รักษา หัวหน้ากิลด์ ยาม หรือเจ้าของกิจการ อาจใช้ความทรงจำและความสัมพันธ์แบบย่อ

### 3.3 ประชากรพื้นหลัง (Population Cohort)

จำลองเป็นกลุ่มตามอาชีพ/ชุมชน เช่น ครัวเรือนชาวนา 12 หลัง แรงงานเหมือง 8 คน ไม่สร้าง AI tree รายคนทุก tick ใช้สมการรวมสำหรับการผลิต การบริโภค และแรงงาน

### 3.4 ระดับการจำลองตามความใกล้/ความสำคัญ

| ระดับ   | ใช้กับ                       | วิธีอัปเดต                                  |
|--------|----------------------------|------------------------------------------|
| ละเอียด | NPC ที่อยู่ในเหตุการณ์สำคัญ/ติดตาม | ประเมินเมื่อมี event และทุก decision interval |
| ปกติ    | NPC สำคัญที่อยู่ในพื้นที่จำลอง      | ประเมินเมื่อถึงรอบกิจกรรมหรือมี trigger         |
| ย่อ     | NPC ที่อยู่ไกล/ประชากรทั่วไป     | รวมผลเป็นรายวันหรือเมื่อสต็อก/สถานะเปลี่ยน       |

ห้ามเปลี่ยนระดับจำลองแล้วให้ผลเศรษฐกิจต่างกันอย่างมีนัยสำคัญโดยไม่มีเหตุ เช่น พื้นที่นอกจอไม่ควรผลิตของฟรีมากกว่าพื้นที่ที่ผู้เล่นดูอยู่

## 4. ข้อมูลภายในของ NPC

### 4.1 โครงสร้างสถานะ

> NPCState
>
> \- identity: id, name, age_band, home, occupation, social_role
>
> \- physical: health, stamina, hunger, fatigue, injury, illness
>
> \- psychological: morale, stress, belonging, fear, confidence
>
> \- attributes: strength, agility, wit, resolve, empathy
>
> \- traits: bravery, caution, generosity, ambition, sociability
>
> \- skills: farming, gathering, crafting, trade, healing, combat, negotiation
>
> \- resources: money, inventory, household_share, equipment
>
> \- commitments: job, shift, party, quest, contract, appointment
>
> \- goals: active_goal, queued_goals, long_term_goal
>
> \- relationships: trust, affinity, respect, grievance, obligation
>
> \- knowledge: known_facts, rumors, confidence, source, learned_at
>
> \- memories: selected_personal_events
>
> \- current_activity: action, location, started_at, expected_end
>
> \- decision_state: last_decision_at, blackboard, random_seed_state

ค่าดิบอาจเป็นช่วง 0–100 แต่ UI ควรแสดงเป็นคำหรือแถบ ไม่เปิดเผยตัวเลขทุกค่า หากไม่มีผลต่อการตัดสินใจที่ผู้เล่นต้องใช้

### 4.2 สภาวะที่คำนวณจากข้อมูลอื่น

หลีกเลี่ยงการบันทึกค่าซ้ำที่คำนวณได้ เช่น:

- “หิวมาก” คำนวณจาก hunger เทียบ threshold

- “ทำงานไม่ได้” คำนวณจาก injury และ fatigue

- “ยากจน” คำนวณจากเงินเทียบค่าใช้จ่ายจำเป็น

- “เส้นทางไม่น่าไว้ใจ” คำนวณจากข่าวภัยที่ NPC รับรู้

วิธีนี้ลดความเสี่ยงที่ค่าหนึ่งอัปเดตแต่อีกค่าค้างเก่า

## 5. ความต้องการและการสลายตัวตามเวลา

ความต้องการเป็นตัวแปรช้า ไม่ต้องอัปเดตทุกวินาที ให้เปลี่ยนตามเวลา/กิจกรรม/เหตุการณ์

| ความต้องการ       | เพิ่มจาก              | ลดจาก                       | ผลเมื่อสูง                  |
|------------------|---------------------|-----------------------------|--------------------------|
| หิว               | เวลาผ่านไป งานหนัก    | กินอาหาร                     | หยุดงาน/ค้นหาอาหาร/ซื้อของ   |
| เหนื่อย            | เดินทาง ต่อสู้ ทำงาน    | พัก/นอน                      | ลดประสิทธิภาพ เลือกกลับบ้าน   |
| ความปลอดภัย       | อยู่ในพื้นที่เสี่ยง บาดเจ็บ  | อยู่ในเมือง/มีผู้คุ้มกัน             | เลือกหลบภัย ขอความช่วยเหลือ  |
| สุขภาพ            | บาดเจ็บ/เจ็บป่วย       | รักษา/พัก                     | ยกเลิกงานหรือหายา          |
| การเป็นส่วนหนึ่ง     | อยู่ลำพัง ถูกปฏิเสธ      | พบเพื่อน/ร่วมกิจกรรม            | ชวนเข้ากลุ่ม/กลับบ้าน         |
| เป้าหมาย/ความหมาย | ล้มเหลว/ขาดความคืบหน้า | ทำเป้าหมายสำเร็จ/พบเป้าหมายใหม่ | หาโอกาสหรือเปลี่ยนเส้นทางชีวิต |

### 5.1 Hysteresis ป้องกันการเปลี่ยนใจไปมา

ใช้ threshold เปิด/ปิดคนละค่า เช่น เริ่มหาอาหารเมื่อ hunger ≥ 70 แต่หยุดถือว่าเร่งด่วนเมื่อ hunger ≤ 40 เพื่อไม่ให้ NPC สลับระหว่าง “ทำงาน” กับ “หาอาหาร” ทุก tick

เพิ่ม minimum commitment เช่น เมื่อเริ่มเดินทางแล้ว ให้ทำต่อจนถึงจุดตัดสินใจ/เกิดเหตุสำคัญ เว้นแต่มีเหตุฉุกเฉิน เช่น บาดเจ็บหนักหรือภัยปิดเส้นทาง

### 5.2 อัตราการเปลี่ยน

ค่า need ไม่ควรแกว่งเร็วเกินไป:

> need_next = clamp(need_now + base_decay × elapsed_game_time
>
> \+ activity_modifier + event_modifier, 0, 100)

อัตรา decay เป็นข้อมูลตั้งค่าตาม need และอาชีพ ไม่ hard-code กระจายหลายระบบ

## 6. Perception: NPC รู้อะไรได้อย่างไร

### 6.1 แหล่งข้อมูล

- **รับรู้โดยตรง:** เห็น/ได้ยินเหตุการณ์ในโหนดปัจจุบัน

- **ข่าวสาร:** NPC อื่น พ่อค้า กิลด์ กระดานข่าว หรือครอบครัวส่งต่อ

- **สัญญาณ/ลางจากกลุ่มดาว:** รับเฉพาะข้อความหรือข้อมูลที่พลังอนุญาต

- **ความทรงจำ:** เหตุการณ์ที่ NPC เคยมีส่วนร่วม

- **อนุมาน:** สรุปจากสิ่งที่รู้ เช่น ร้านยาปิดหลายวันจึงคาดว่ายาขาด

### 6.2 ความน่าเชื่อถือของข้อมูล

> Belief = {fact_or_claim, confidence 0..1, source, observed_at, expires_at}

- พบเอง: ความเชื่อมั่นสูง

- ข่าวจากคนไว้ใจ: สูง/กลางตามความสัมพันธ์

- ข่าวลือจากแหล่งไม่ชัด: ต่ำ

- ข่าวเก่า: ลดความเชื่อมั่นเมื่อเวลาผ่านไป

- ข้อมูลขัดแย้ง: เก็บหลาย claim ได้ ไม่ลบข้อมูลเดิมทันที

### 6.3 จำกัดขอบเขตการรับรู้

NPC ไม่รู้โดยอัตโนมัติว่า:

- สินค้าทั้งโลกมีเท่าไร

- ผู้เล่นคนอื่นใช้พลังอะไร

- เหตุการณ์ในพื้นที่ห่างไกลเกิดขึ้นแล้วหรือยัง

- ภารกิจลับหรืออันตรายที่ไม่มีผู้ใดรายงาน

นี่เป็นเงื่อนไขสำคัญเพื่อให้การเดินทาง ข่าวสาร และพ่อค้ามีบทบาทจริง

## 7. Utility AI: เลือก “เป้าหมายใดสำคัญที่สุด”

### 7.1 เป้าหมายที่เป็น candidate

ตัวอย่างชุดเป้าหมาย:

- กิน/หาอาหาร

- นอน/พักฟื้น

- รักษา/หายา

- ไปทำงาน/ผลิตสินค้า

- ซื้อวัตถุดิบ/ขายส่วนเกิน

- ส่งสินค้าหรือเดินทางค้าขาย

- ช่วยครอบครัว/เพื่อน

- รับหรือทำภารกิจ

- ฝึกทักษะ

- เข้าสังคม/พักผ่อน

- เปลี่ยนอาชีพ/หางาน

- หนีภัย/หาที่ปลอดภัย

ไม่สร้าง candidate ทุกชนิดให้ NPC ทุกครั้ง สร้างเฉพาะจากสถานะและ trigger ปัจจุบัน เช่น NPC ที่ไม่มีอาชีพว่างจึงค่อยพิจารณาหางาน

### 7.2 คะแนนพื้นฐาน

> utility(goal) = urgency
>
> × personal_value
>
> × feasibility
>
> × information_confidence
>
> \+ trait_fit
>
> \+ relationship_value
>
> \+ opportunity_value
>
> \- risk_cost
>
> \- time_cost
>
> \- money_cost
>
> \- commitment_break_cost

แปลงองค์ประกอบให้อยู่ในช่วงมาตรฐานก่อนรวม เช่น 0–1 สำหรับตัวคูณ และ -100 ถึง +100 สำหรับโบนัส/โทษ จากนั้น clamp คะแนนสุดท้ายให้อยู่ในช่วงที่กำหนด

### 7.3 ความหมายขององค์ประกอบ

- **urgency:** ความเร่งด่วนจากความต้องการ/กำหนดเวลา

- **personal_value:** เป้าหมายนี้สำคัญต่อบุคลิกหรือชีวิต NPC แค่ไหน

- **feasibility:** มีทักษะ เงิน ของ เวลา และสิทธิ์เข้าพื้นที่หรือไม่

- **information_confidence:** NPC เชื่อว่าความพยายามนี้มีโอกาสได้ผลเพียงใด

- **trait_fit:** บุคลิกเข้ากับการกระทำนั้นหรือไม่

- **relationship_value:** ช่วยคนสำคัญหรือทำงานกับคนที่ไว้ใจหรือไม่

- **opportunity_value:** โอกาสหายาก เช่น ฤดูเก็บเกี่ยวหรือราคาสินค้าสูง

- **risk/time/money cost:** ต้นทุนที่ประเมินไว้

- **commitment_break_cost:** โทษจากการผิดสัญญา/ทิ้งงานกลางทาง

### 7.4 การเลือกไม่ให้เหมือนหุ่นยนต์

หลังคำนวณคะแนน:

- เลือก goal ที่คะแนนสูงสุดเมื่อสูงกว่าค่าเริ่มต้นขั้นต่ำ

- ถ้าคะแนนใกล้กันมาก ให้สุ่มแบบ weighted ด้วย seed เพื่อเพิ่มความหลากหลาย

- การสุ่มต้องไม่เอาชนะ safety override หรือความจำเป็นระดับวิกฤต

- ผูกการตัดสินใจไว้ช่วงหนึ่งด้วย commitment เพื่อไม่ให้ NPC คิดใหม่ทุก tick

### 7.5 อธิบายเหตุผล

เก็บ 1–3 ปัจจัยที่มีน้ำหนักสูงสุด เช่น:

“เลือกไปซื้อยา เพราะสมาชิกครอบครัวป่วย สต็อกในบ้านเหลือไม่ถึงหนึ่งวัน และร้านในเมืองมีของตามข่าวล่าสุด”

ข้อความสรุปมาจากข้อมูลการประเมินจริง ไม่ควรให้ระบบเขียนเหตุผลย้อนหลังที่ไม่ตรงกับคะแนน

## 8. Behavior Tree: ลงมือทำเป้าหมายอย่างไร

Utility AI เลือก goal หนึ่งรายการแล้วส่งให้ Behavior Tree ที่เหมาะสม BT ทำงานเป็นโหนดย่อยและไม่ประเมินเป้าหมายทั้งโลกซ้ำทุกเฟรม

### 8.1 ความหมายโหนดพื้นฐาน

- **Selector:** ลองลูกตามลำดับจนมีอันหนึ่งสำเร็จ

- **Sequence:** ทำลูกตามลำดับ; ลูกใดล้มเหลวให้ sequence ล้มเหลว

- **Condition:** ตรวจสถานะโดยไม่เปลี่ยนโลก

- **Action:** ส่งคำสั่งไป resolver; ไม่แก้สถานะโดยตรง

- **Wait/Event:** รอเวลา/ผล/ข่าวที่จำเป็น

- **Decorator:** จำกัดจำนวนครั้ง เวลา หรือเงื่อนไข

สถานะโหนดควรมีอย่างน้อย <u>SUCCESS</u>, <u>FAILURE</u>, <u>RUNNING</u>, <u>SUSPENDED</u> เพื่อแยก “กำลังเดินทาง” ออกจาก “ล้มเหลว” และ “หยุดชั่วคราวเพราะเหตุใหม่”

## 10. Interrupt และการเปลี่ยนแผน

Interrupt ที่อนุญาต

- บาดเจ็บวิกฤต/สุขภาพลดต่ำกว่าค่าปลอดภัย

- ภัยเกิดใกล้ตัวหรือเส้นทางถูกปิด

- ร้าน/งานที่กำลังไปถูกทำลายหรือไม่มีสินค้าแล้ว

- ครอบครัว/สมาชิกปาร์ตี้ต้องการความช่วยเหลือเร่งด่วน

- ภารกิจหมดเวลา หรือสัญญาถูกยกเลิก

- เป้าหมายเสร็จแล้วหรือไม่มีทางทำต่อ

Interrupt ที่ไม่ควรทำ

- เปลี่ยนเป้าหมายเพียงเพราะคะแนน utility ขยับเล็กน้อย

- รับข่าวลือใหม่แล้วเลิกสัญญาทันทีโดยไม่มีการประเมินความน่าเชื่อถือ

- เลิกทำงานเพราะราคาสินค้าแกว่งเล็กน้อย

- เปลี่ยนเส้นทางไปมาทุก tick เพราะมีทางเลือกใหม่ที่คะแนนสูงกว่าเล็กน้อย

กฎ commitment

เมื่อเริ่มเป้าหมาย ให้บันทึก:

> Commitment = {goal_id, started_at, minimum_commitment_until,
>
> abort_conditions, sunk_cost, expected_completion}

การละทิ้งแผนมีต้นทุนตามเวลา เงิน ความสัมพันธ์ หรือคำมั่นที่ลงทุนไป แต่เหตุฉุกเฉินสามารถ override ได้

## 11. พฤติกรรมเศรษฐกิจของผู้มีบทบาทต่างกัน

### 11.1 ครัวเรือน/ผู้บริโภค

- คาดการณ์ของจำเป็นตามขนาดครัวเรือนและช่วงเวลาที่ต้องการครอบคลุม

- ซื้อเมื่อสต็อกต่ำกว่าจุดสั่งซื้อและมีเงินพอ

- ปกป้องเงินสำหรับอาหาร/ยา ก่อนซื้อของไม่จำเป็น

- เลือกสินค้าทดแทนตามราคาและคุณภาพ

- ไม่ซื้อเกินคลัง/อายุสินค้าที่ใช้ได้จริง

### 11.2 ผู้ผลิต

- วางแผนรอบผลิตจากสต็อกปัจจุบัน คำสั่งซื้อ และความต้องการคาดการณ์

- ตรวจวัตถุดิบ ค่าแรง กำลังผลิต และพื้นที่เก็บ

- หากขาด input ให้เลือกผู้ขาย/สินค้าแทน/ลดกำลังผลิต

- หากสินค้าค้างสต็อกมาก ลดรอบผลิตหรือปรับราคาตามกฎ ไม่สร้างของเพิ่มเพื่อระบาย

### 11.3 ร้านค้า

- ตั้งราคาแยกซื้อ/ขาย

- กันเงินทุนสำหรับการสั่งซื้อและค่าใช้จ่าย

- สั่งสินค้าโดยหักของที่กำลังขนส่งออกจากความต้องการ

- มีเครดิต/งบจำกัด ไม่สามารถซื้อของจาก NPC ทุกคนโดยไม่จำกัด

### 11.4 พ่อค้า

- พิจารณากำไรหลังหักต้นทุนเดินทาง ภาษี ความเสี่ยง และเวลาที่เงินจม

- มีข้อมูลเฉพาะตลาดที่เคยรู้/มีข่าวถึง

- ไม่ส่งสินค้าจำเป็นออกจากพื้นที่ที่ต่ำกว่า safety stock

- ลดหรือหยุดเส้นทางหากขาดทุน/อันตรายต่อเนื่อง

### 11.5 กิลด์/หน่วยงาน

- จัดลำดับปัญหาชุมชนตามภัย ความเร่งด่วน และงบที่มี

- ตั้งรางวัลจากเงินจริง/สิ่งของในคลังที่มี

- หากงบไม่พอ ลดขอบเขตภารกิจหรือขอทุน ไม่สร้างเงินอัตโนมัติ

- ติดตามผลภารกิจและปรับแผนตามข้อมูลใหม่

## 12. วงจรตัดสินใจและรอบประเมิน

กำหนดเวลาประเมินต่างกันตามชนิดการกระทำ เพื่อลด CPU และไม่ทำให้ AI รู้สึกกระตุก

| ประเภทการประเมิน          | ความถี่ตั้งต้น                           | เหตุผล                    |
|--------------------------|-------------------------------------|--------------------------|
| Need decay/สถานะพื้นฐาน    | รวมตามรอบเวลา/เหตุการณ์               | ไม่จำเป็นต้องอัปเดตทุกเฟรม    |
| Utility goal selection   | ทุก 1–2 ช่วงเวลาในเกม หรือเมื่อมี trigger | ป้องกันการเปลี่ยนใจถี่         |
| BT activity step         | เมื่อ action เสร็จ/เดินทางถึง/ได้รับผล     | ใช้ event-driven          |
| ราคา/สั่งซื้อร้าน             | วันละครั้งในรอบเศรษฐกิจ                 | ป้องกันราคาแกว่งและคำนวณซ้ำ  |
| Perception/news delivery | เมื่อข่าวมาถึง NPC/พื้นที่                  | จำลองการไหลของข้อมูล       |
| Background cohort        | รายวันหรือเมื่อสถานะเศรษฐกิจเปลี่ยน        | ประหยัดทรัพยากร            |
| NPC ที่กำลังต่อสู้/วิกฤต        | ทุก combat beat หรือเหตุการณ์สำคัญ       | ต้องตอบสนองเร็วกว่า routine |

ตัวเลขรอบเวลาต้องสอดคล้องกับความเร็วเวลาโลกของเกม แต่ไม่ควรผูกการจำลองกับ frame rate

## 13. วิธีสร้างความแตกต่างระหว่าง NPC

ให้ความแตกต่างเกิดจากพารามิเตอร์และประวัติ ไม่ใช้ AI คนละชุดทั้งหมด

### 13.1 Traits

บุคลิกเริ่มต้นมี 4–6 ค่า เช่น:

- ความกล้าหาญ

- ความระมัดระวัง

- ความทะเยอทะยาน

- ความเอื้อเฟื้อ

- ความเข้าสังคม

- ความอดทนต่อความเสี่ยง

ใช้เป็นตัวคูณ/โบนัสของ utility ไม่ใช่คำสั่ง hard-coded

### 13.2 Skills

ทักษะมีผลต่อ feasibility และคุณภาพผลลัพธ์ เช่น ผู้รักษาที่มีทักษะสูงเลือกการรักษาได้หลายแบบ ใช้ยาน้อยกว่า หรือฟื้นตัวได้ดีขึ้น แต่ไม่ทำให้ทำสิ่งที่ไม่มีเครื่องมือ/วัตถุดิบได้

### 13.3 ประวัติส่วนบุคคล

ความทรงจำเปลี่ยนแรงจูงใจเฉพาะ:

- เคยถูกทิ้งระหว่างภารกิจ → ลดความไว้ใจในผู้ชวน

- เคยช่วยชุมชนได้สำเร็จ → เพิ่มความสนใจภารกิจชุมชน

- เคยบาดเจ็บหนักในป่า → เพิ่ม risk cost ของเส้นทางป่า

- เคยผิดสัญญาแล้วเสียชื่อ → เพิ่ม commitment cost ก่อนรับงานใหม่

### 13.4 ความสัมพันธ์

ความไว้ใจ ความชอบ ความเคารพ และความคับข้องใจแยกกัน ไม่ใช้คะแนนเดียวแทนความสัมพันธ์ทั้งหมด เช่น NPC อาจไม่ชอบหัวหน้าปาร์ตี้แต่ยังเคารพฝีมือและทำตามแผนฉุกเฉินได้

## 14. การสื่อสารเหตุผลของ AI ต่อผู้เล่น

ผู้เล่นต้องเห็นสิ่งที่จำเป็นต่อการตีความ แต่ไม่จำเป็นต้องเห็นสูตรทั้งหมดตลอดเวลา

ระดับข้อมูล

- **สรุป:** “กลับเมือง เพราะเสบียงใกล้หมด”

- **รายละเอียด:** “เสบียงเหลือประมาณ 1 วัน; เป้าหมายเดิมใช้เวลาเดินทางกลับ 2 ช่วง; เพื่อนบาดเจ็บ”

- **โหมดวิเคราะห์ (optional):** คะแนน goal โดยประมาณและองค์ประกอบที่มีน้ำหนักสูง

ไม่ควรแสดงค่าความน่าจะเป็นที่ดูแม่นยำ หากระบบมีความไม่แน่นอนจากข่าวหรือการสุ่ม

บันทึกเหตุผล

ทุกการตัดสินใจสำคัญบันทึก:

> DecisionTrace
>
> \- actor_id
>
> \- time
>
> \- chosen_goal/action
>
> \- candidate_summary (เฉพาะ top 3-5)
>
> \- top_reasons
>
> \- rejected_due_to (เงิน/ทักษะ/ภัย/commitment)
>
> \- information_used
>
> \- random_seed/reference

ไม่เก็บ trace ของทุก candidate ทุก tick ถาวร เพราะสิ้นเปลืองหน่วยเก็บข้อมูล ให้เก็บเต็มเฉพาะ debug หรือเหตุการณ์สำคัญ และเก็บสรุปสำหรับพงศาวดาร

## 15. กรณีตัวอย่าง AI ตัดสินใจเศรษฐกิจ

สถานการณ์

เรน่าเป็นนักผจญภัย มีเงิน 35 เหรียญ อาหารเหลือหนึ่งวัน ได้รับคำชวนภารกิจเก็บสมุนไพรที่ใช้เวลาสามวัน เธอมีเป้าหมายช่วยหมู่บ้าน แต่ปาร์ตี้ยังขาดยาและข้อมูลภัยในป่ายังไม่ครบ

การประเมิน Utility

| เป้าหมาย             | คะแนนตัวอย่าง | เหตุผลหลัก                                   |
|---------------------|-------------|--------------------------------------------|
| รับภารกิจทันที          | 42          | ตรงเป้าหมายส่วนตัวและมีค่าตอบแทน                |
| ซื้ออาหาร/ยาแล้วค่อยออก | 71          | ลดความเสี่ยงและยังทำภารกิจทันกำหนด              |
| พักหนึ่งช่วง            | 58          | เพิ่มความพร้อม แต่เสียเวลาและกำหนดภารกิจใกล้เข้ามา |
| ปฏิเสธภารกิจ          | 25          | ลดความเสี่ยง แต่ขัดกับเป้าหมายช่วยหมู่บ้าน           |

Utility AI เลือกเตรียมของก่อน จากนั้น BT ซื้ออาหาร/ยาในงบที่มี หากเงินไม่พอ จะลองลดจำนวน ซื้อยาทดแทน หรือขอให้ปาร์ตี้แบ่งเสบียง ก่อนยกเลิกภารกิจ

ผู้เล่นกลุ่มดาวอาจส่งลางว่าป่ามีภัย แต่ไม่สามารถสั่งเรน่าให้ออกทางเหนือหรือสั่งให้เธอจ่ายเงินทั้งหมดไปกับยา

## 16. การจำลองแบบออนไลน์และการประหยัดทรัพยากร

### 16.1 Event-driven first

อย่าประเมิน Utility AI ของ NPC ทุกคนทุกวินาที ประเมินเมื่อ:

- ความต้องการข้าม threshold

- action ปัจจุบันเสร็จ

- ข่าวใหม่มาถึง

- ราคา/สต็อกเปลี่ยนจนกระทบแผน

- เป้าหมายหมดเวลา/ล้มเหลว

- ความสัมพันธ์เปลี่ยนอย่างมีนัยสำคัญ

- เกิดภัย/เหตุการณ์ฉุกเฉิน

- ถึง decision interval ตามอาชีพ

### 16.2 แยกคำนวณเป็น batch

- รวมการลด hunger/fatigue เป็นค่า delta ตามเวลาผ่านไป

- ประมวลผล cohort และกิจการเป็น batch ต่อรอบเศรษฐกิจ

- วางคิว NPC ที่ต้องประเมินใหม่ แล้วจัดลำดับตามความเร่งด่วน

- ประมวลผลเฉพาะ top candidate แทนสร้าง action ทั้งหมด

- ใช้ cache สำหรับข้อมูลราคา/เส้นทางจนกว่าจะมี event invalidation

### 16.3 LOD ของ AI

- ตัวละครที่ผู้เล่นติดตามหรืออยู่ในเหตุการณ์: ความละเอียดสูง

- NPC สำคัญในพื้นที่เดียวกัน: ความละเอียดปกติ

- NPC ในพื้นที่ห่างไกล: คำนวณผลรวม/ตัวแทนเชิงเศรษฐกิจ

- เมื่อตัวละครย้ายเข้าสู่พื้นที่ที่ผู้เล่นติดตาม ให้ hydrate จากสถานะย่อ แล้วใช้กฎเดียวกันต่อ

### 16.4 ข้อจำกัดด้านงานต่อ tick

ตั้ง budget ภายในต่อรอบจำลอง เช่น จำนวน NPC ที่อนุญาตให้ re-evaluate และจำนวน path/utility query สูงสุด หากเกิน ให้จัดคิวต่อในรอบถัดไปตามความสำคัญ แทนการคำนวณทั้งหมดพร้อมกันจนเซิร์ฟเวอร์สะดุด

## 17. Online consistency, determinism และการป้องกันความผิดพลาด

- เวลาโลก การเงิน สต็อก การเดินทาง และผลจาก AI ตัดสินบนเซิร์ฟเวอร์

- Client ขอ “ทำ action” ไม่ส่งคำตอบสุดท้ายว่าซื้อ/ผลิต/ชนะแล้ว

- คำสั่งซื้อใช้ atomic transaction: ตรวจสต็อก/เงินและหักพร้อมกัน

- ใช้ idempotency key ป้องกันคำขอเครือข่ายซ้ำ

- ใช้ server seed สำหรับผลสุ่มและเก็บ reference ใน event log

- การคำนวณ AI ที่ต้องทำซ้ำใช้เวอร์ชันกฎเดียวกันและ snapshot สถานะเดียวกัน

- เมื่อปรับสูตร AI ระหว่าง live world ให้ version behavior rules และมี migration/ค่อย ๆ rollout

- ป้องกัน race condition กรณี NPC สองคนซื้อของชิ้นสุดท้ายหรือกิจการสองแห่งแย่งวัตถุดิบเดียวกัน

## 18. การทดสอบ AI

### 18.1 Unit tests

ทดสอบกฎเฉพาะ เช่น:

- hunger สูงกว่าค่าวิกฤตทำให้เป้าหมายอาหารมี priority สูงขึ้น

- ไม่มีเงิน/สต็อกทำให้ BT ไม่ส่งคำสั่งซื้อที่เป็นไปไม่ได้

- NPC ไม่รับข่าวที่ไม่ได้มาถึง

- commitment ป้องกันการเปลี่ยนแผนเมื่อคะแนนต่างกันเพียงเล็กน้อย

- safety interrupt ทำงานแม้อยู่ระหว่างภารกิจ

### 18.2 Simulation tests

จำลอง NPC หลายร้อย/หลายพันรอบแบบไม่เรนเดอร์ ตรวจ:

- NPC ไม่ติดลูปเดินทางไปมา

- ความต้องการไม่ค้างเต็ม/ต่ำสุดโดยไม่มีการตอบสนอง

- เศรษฐกิจไม่สร้าง/หักสินค้าและเงินผิดบัญชี

- NPC ไม่ใช้เงินซื้อของที่ไม่มีประโยชน์หรือเกินกำลังจ่าย

- กิจการไม่ผลิตเมื่อไม่มีวัตถุดิบ/แรงงาน

- ข่าวลือเดินทางและหมดอายุอย่างสมเหตุสมผล

- ผลลัพธ์ทำซ้ำได้เมื่อใช้ seed เดิม

### 18.3 Playtest questions

- ผู้เล่นอ่านเหตุผลของการกระทำล่าสุดได้หรือไม่?

- NPC ดูมีนิสัยต่างกันหรือแค่ทำตามคะแนนเดียวกัน?

- ผู้เล่นเข้าใจว่าทำไมร้านของหมดหรือราคาขึ้นหรือไม่?

- NPC เปลี่ยนแผนมากเกินไปหรือยึดแผนเดิมนานเกินไป?

- เหตุการณ์ที่ผู้เล่นไม่เห็นยังรู้สึกน่าเชื่อถือเมื่อนำมาเล่าภายหลังหรือไม่?

## 19. ขอบเขต MVP สำหรับ NPC AI

ทำก่อน

1.  Need system แบบ 4–5 ค่า

2. Utility goal selection ที่มี candidate จำกัด

3. BT สำหรับพัก/กิน/ทำงาน/ซื้อของ/เดินทาง/ภารกิจ

4. ระบบ perception ข่าวสารแบบ confidence

5. commitment และ interrupt

6. transaction resolver สำหรับซื้อขายและผลิต

7. event log พร้อม reason summary

8. LOD: named NPC รายบุคคล, population cohort แบบรวม

ยังไม่ทำ

- LLM-driven personality หรือบทสนทนาอิสระเป็นตัวกำหนดผลเกม

- การวางแผนอัตโนมัติหลายร้อยขั้น

- จำลองสมอง/อารมณ์ละเอียดระดับชีววิทยา

- แผนที่นำทางเชิงเรขาคณิตซับซ้อน หากโหนดและเส้นทางเพียงพอ

- จำลอง NPC ทุกคนในโลกแบบ full fidelity

- ระบบการเมืองหลายฝ่ายที่มีอำนาจและกฎหมายซับซ้อนก่อนเศรษฐกิจหลักทำงาน
